# 07 · 单元测试

> 面向：**修改框架代码的人**。
> 读完能回答三个问题：怎么跑、跑出来什么、改了代码之后我该加什么测试。

---

## 一、这是什么

框架里有两套测试，职责完全不同，**不要混淆**：

| | `testcase/` | `tests/` |
| --- | --- | --- |
| 被测对象 | **被测业务系统**（内网接口） | **本框架自身代码** |
| 依赖 | 真实服务、真实数据、网络 | 无（全部离线） |
| 运行时长 | 秒~分钟 | 约 10 秒 |
| 失败含义 | 业务系统有问题 | **框架代码被改坏了** |
| 数据文件 | 会读取真实 Excel/YAML | 只读副本，**绝不改动 `data/`** |
| 何时跑 | 提交后 / 构建后 / 每日回归 | 改任何框架代码后、提交前、CI 最初阶段 |

一句话：`tests/` 保证「**测试工具本身是准的**」，`testcase/` 保证「业务系统是好的」。
如果框架有 bug，`testcase/` 的失败原因会被误导——所以先保住 `tests/`。

### 为什么要有两个「测试」目录

```
testcase/   业务用例    519 行 · 连内网 · 会读写 data/     ← 日常写用例就在这里
tests/      框架自测   6755 行 · 全离线 · 只读 data/      ← 只有改了框架代码才需要碰
```

框架本体（`api` / `common` / `utils` / `config` / `testcase` / `tools` / `main.py`）
合计 5862 行，而 `tests/` 有 6755 行 —— **测试代码比被测代码还多，这是正常的**：
一次性的编写成本，换掉后续每一次「改了框架心里没底」的不确定性。

### 新手最容易误读的四点

| 常见误读 | 事实 |
| --- | --- |
| `tests/` 是「更全的用例集合」 | 反了。`tests/` 测的是**框架自己**；业务用例在 `testcase/` |
| 裸跑 `pytest` 会把 `tests/` 也跑了 | 不会。`pytest.ini` 的 `testpaths = testcase` 只收业务用例，跑框架自测必须显式写 `pytest tests` |
| 把业务用例写进 `tests/` 也能执行 | 会在**收集阶段直接报错**——`tests/` 禁止 `network` / `mysql` 标记，因为它在 CI 里必须离线全绿 |
| 读框架代码应该从 `tests/` 入手 | 不建议。那里满是替身对象与 `monkeypatch`，是「怎么被验证的」而非「怎么设计的」，先读 `api/base_api.py` |

> 两个目录名只差一个字母，是新人最常踩的坑，故在 `testcase/__init__.py` 与
> `tests/__init__.py` 的包注释里都写明了边界；IDE 里点进去就能看到。

## 二、快速运行

```bash
# 全部单元测试（推荐日常使用）
python -m pytest tests

# 简洁输出
python -m pytest tests -q

# 只看某个模块
python -m pytest tests/test_common_base.py
python -m pytest tests/test_api_base_api.py

# 按关键字挑
python -m pytest tests -k "excel or yaml"

# 失败即停 + 显示完整堆栈
python -m pytest tests -x --tb=long

# 顺便跑静态检查与环境预检（提交前一把过）
python -m flake8 .
python tools/preflight.py
```

当前规模：**1134 个用例 / 24 个 `test_*.py` 文件，约 10 秒跑完**（全离线，不起服务、不连数据库）。

## 五、六条铁律

新增单元测试时必须遵守，否则会污染真实数据或产生偶发失败。

### 铁律 1：绝不碰真实数据

```python
# ❌ 会修改仓库里的用例文件
util = ExcelUtil()
util.update_result(2, {}, True)

# ✅ 用 fixture 生成的临时副本
def test_something(excel_file):
    util = ExcelUtil(excel_file, "test_case_list")
    util.update_result(2, {}, True)
```

`excel_file` 与 `yaml_dir` 两个 fixture 会在 `tmp_path` 下生成结构完整的样本（含空行、停用行、多标签行），
既不改真实文件，也能覆盖边界。

### 铁律 2：网络请求一律用替身

```python
# ✅ 用 FakeSession 拦截，可断言发出的参数
def test_request(monkeypatch):
    session = FakeSession(FakeResponse(payload={"status": 200}))
    api = BaseApi(base_url="http://host", session=session)
    api.request("get", "/v1/x", data={"a": 1})
    assert session.last_call["kwargs"]["params"] == {"a": 1}
```

**永远不要在单元测试里请求真实地址**——那会让测试依赖环境、变慢，并可能在 CI 里随机失败。

这条不是靠自觉，而是**机器拦截**：`tests/conftest.py` 的 `pytest_collection_modifyitems`
会在收集阶段扫描所有用例，只要发现 `@pytest.mark.network` 或 `@pytest.mark.mysql`，
立刻抛出 `UsageError` 并列出违规用例的 nodeid —— 让问题在「收集」就暴露，而不是跑起来后
报一串 `ConnectionError`。依赖真实环境的用例请放 `testcase/`。

### 铁律 3：靠 fixture 做状态隔离，不要手写 setUp/tearDown

`tests/conftest.py` 里的 `isolate_state` 会在**每个用例前后**自动：

- 清空 `GlobalVar` 变量池
- 清空 `ExcelUtil` 的工作簿缓存与脏标记
- 清空系统适配档案缓存（`profile.clear_cache()`）
- 快照并恢复 `settings.RunConfig` / `settings.DB_CONFIG`
- 快照并恢复另外四组配置：`LogConfig` / `ReportConfig` / `AuthConfig` / `CIConfig`
- 快照并恢复 `settings.ENV_OVERRIDES`（被 `AMSAPI_*` 覆盖过的配置项集合）

所以用例里可以放心改配置（例如 `settings.RunConfig.WRITE_BACK = False`），不会影响其它用例。

> **为什么连 `ENV_OVERRIDES` 也要隔离**：它由 `settings._load_env()` 写入，
> 语义是「哪些项被环境变量覆盖过」，直接决定**档案取超时/证书校验时的优先级**。
> 测试里用 `monkeypatch.setenv()` + `_load_env()` 能撤销环境变量，却撤不掉这个集合里的记录，
> 于是「超时被环境变量覆盖」的状态会泄漏给后续用例 ——
> 表现为「档案里明明写了 `timeout = 25`，读出来却是 `conf.ini` 的默认值 10」，
> 而且单跑那个文件是绿的、全量跑才红，极难定位。

### 铁律 4：不得写入真实环境信息（开源守卫）

本仓库要开源给他人使用，因此**任何真实的内网地址、账号、口令、签名值、系统代号、
业务数据标识都不允许出现在仓库里**——包括代码、配置、注释、文档、Excel 内容。

这条同样由机器拦截：`tests/test_repo_sanitized.py` 会扫描全仓文本文件与
`data/api_tables.xlsx`，命中黑名单片段即失败；它还会校验：

- `config/systems/*.ini` 档案文本里不含真实信息
- 仓库自带的示例用例**必须使用相对路径**（真实域名只允许来自 `AMSAPI_BASE_URL` 或档案）
- `settings.DB_CONFIG["password"]` 必须为空（仓库不预置任何可用凭据）

写新用例/文档时的替换约定：

| 类型 | 用这个 |
| --- | --- |
| 域名 / IP | `https://api.example.com`、`192.0.2.10`（RFC 5737 文档用网段） |
| 账号 / 口令 | `demo_user` / `demo_password` |
| 应用 / 组织编码 | `demo-admin` / `demo-app` / `demo-org` |
| 系统代号 | `gov` / `finance_erp` / `mall` / `dataplatform` |
| 用例 url | 相对路径，如 `/v1/users/login` |

> 守卫代码自身用了**片段拼接**（`"".join([...])`）来写黑名单，
> 否则它自己就会命中自己的规则 —— 这是新增黑名单关键字时唯一需要留意的细节。

### 铁律 5：换台机器也一样绿 —— 环境变量必须隔离

CI 里常用 `AMSAPI_*` 注入环境（`AMSAPI_BASE_URL` / `AMSAPI_LOG_DIR` / `AMSAPI_SYSTEM` …），
而 `settings.py` 的路径常量与运行配置是在**模块导入时**就定型的。若不处理，就会出现
「本地全绿、流水线红一片」：单测断言的是框架默认行为，却被 CI 注入的值串掉。

`tests/conftest.py` 的做法是：在 `from config import settings` **之前**把全部 `AMSAPI_*`
从 `os.environ` 摘除（并备份），日志/报告强制指向
`%TEMP%\amsapi-unittest-artifacts\`，会话结束在 `pytest_unconfigure` 里原样还原。

因此：

- 新增单测时**不要**依赖外部注入的 `AMSAPI_*`；
- 确需验证「环境变量覆盖配置」时，用 `monkeypatch.setenv(...)` + `settings._load_env()`，
  作用域仅限该用例；
- **不要把单测的日志/报告写进仓库**，否则会产生无意义的 git 变更。

### 铁律 6：新增会打印请求/响应的代码，必须经脱敏

日志与 Allure 附件会随构建制品归档、被转发给非相关同学，
**明文口令 / 令牌等价于口令外泄**。

```python
# ❌ 绕过脱敏，明文直接落盘
logger.debug("params = %s", params)

# ✅ 日志由 SensitiveFilter 自动接管（挂 root logger，无需手动调用）
logger.debug("params = %s", params)

# ✅ 写附件时显式走脱敏入口（allureutil 内部已调用，自定义附件请照做）
allureutil.attach_json("请求体", mask.mask_payload(payload))
```

- 日志路径：`utils/logutil.py` 的 `SensitiveFilter` 挂在 root logger 上，
  `logger.*` 的 `msg` 与 `args` 都会被递归打码，**业务代码无需改动**。
- 附件路径：`utils/allureutil.py` 的四个 `attach_*` 已内置脱敏；
  若自行调用 `allure.attach(...)`，请先过 `common/mask.py`。
- 验证方式：`tests/test_common_mask.py` 覆盖字段名识别、打码模式、
  `Bearer` 令牌、日志 Filter 集成；新增敏感字段名用 `[mask] extra_keys` 扩展并补一条单测。

## 六、可复用的替身对象

全部定义在 `tests/conftest.py`，直接 `from tests.conftest import ...` 使用。

| 替身 | 替代 | 用途 |
| --- | --- | --- |
| `FakeResponse` | `requests.Response` | 构造状态码 / JSON / 非 JSON / cookie 响应 |
| `FakeSession` | `requests.Session` | 记录每次请求的 method/url/kwargs，可排队返回多个响应或抛异常 |
| `FakePymysql` | `pymysql` 模块 | 离线验证连接、游标、提交回滚 |
| `FakeDbMysql` | `MysqlUtil` | 记录 SQL 与参数，供数据访问层断言 |
| `FakeApiClient`（在 `test_testcase_layer.py`） | `BaseApi` | 记录请求要素，供 SQL 驱动测试 |

常用 fixture：

| fixture | 提供 |
| --- | --- |
| `fake_session` | 默认返回 `200 + {"status": 200}` 的会话替身 |
| `excel_file` | 临时 Excel 样本（3 个 sheet，5 行用例） |
| `yaml_dir` | 临时 YAML 用例目录（含非法项与非 yaml 文件） |

## 七、动手加一个单元测试

**场景**：给 `common/base.py` 新增了 `parse_tags()` 的边界处理，想加一条测试。

1. 找到对应文件 `tests/test_common_base.py`，定位到同类测试类（如 `TestTags`）
2. 按现有风格追加：

```python
class TestTags:
    def test_parse_tags_deduplicate(self):
        """重复标签只保留一次。"""
        assert base.parse_tags("smoke,smoke") == ["smoke"]
```

3. 跑一下：

```bash
python -m pytest tests/test_common_base.py -k dedup -q
```

**命名与风格约定**：

| 项 | 约定 |
| --- | --- |
| 测试类 | `TestXxx`，对应被测函数/类 |
| 测试方法 | `test_<行为>_<条件>`，用中文 docstring 说明「为什么测这条」 |
| 断言 | 一条测试聚焦一个行为；报错信息要能直接定位问题 |
| 参数化 | 多组输入用 `@pytest.mark.parametrize`，不要写多个近似方法 |
| 中文 | 注释与 docstring 用中文，与框架其余部分一致 |

**修改了框架代码的提交前清单**：

- [ ] `python -m pytest tests` 全绿（含开源守卫 `test_repo_sanitized.py`）
- [ ] 新增/修改的行为，在 `tests/` 里有对应用例
- [ ] 覆盖率没有明显下降（新增分支要覆盖）
- [ ] `python main.py --collect-only` 仍能收集到用例（确认没改坏业务链路）
- [ ] 更新 `CHANGELOG.md`

## 八、在 CI 中的位置

`Jenkinsfile` 中单元测试排在**接口测试之前**：

```
检出代码 → 准备环境 → 静态检查 → 环境预检 → 数据与配置自检 → 【框架单元测试】→ 冒烟/全量回归
                                                              ↑ 约 10 秒，不依赖被测环境
```

理由：框架自身坏了的话，后面的接口测试结果没有参考价值，先失败先止。
命令就是 `python -m pytest tests -q`（流水线里另加 `--cov-fail-under=${COVERAGE_MIN}` 守覆盖率下限）。
`静态检查`（`python -m flake8 .`）与 `环境预检`（`python tools/preflight.py`）在它之前，
秒级拦掉语法问题与环境问题，避免「依赖没装 / 域名配错」被误读成一堆业务用例失败。

详见 [06-CICD集成](06-CICD集成.md)。

## 九、常见问题

### Q1 跑 `pytest` 为什么没跑单元测试？

`pytest.ini` 里 `testpaths = testcase`，默认只收集业务用例。
跑框架自测请显式指定目录：`python -m pytest tests`。

### Q2 单元测试会不会改动 Excel 或 YAML 数据？

不会。Excel 相关用例全部在 `tmp_path` 的副本上执行，且有专门用例
（`test_readonly_run_does_not_touch_file`、`test_dirty_is_per_file`）锁定这一行为。
已实测：跑完全部单测后 `data/` 与 `report/` 的文件校验值完全不变。

### Q3 日志里出现 `_pytest.logging.LogCaptureHandler`，是不是框架重复挂了 handler？

不是。pytest 的 logging 插件会把自身的 handler 挂到所有已存在的 logger 上。
判断框架是否重复挂 handler 要看过滤后的数量（`test_utils_logutil.py` 的 `_own_handlers()` 有示范）。

### Q4 用例在本地全绿，在 Jenkins 上失败？

先确认是不是被环境变量影响。CI 会注入 `AMSAPI_*`，可能改变数据源、冒烟开关等。
单元测试已按四种环境组合验证过（默认 / CI 全量 / CI 冒烟 / CI 冒烟无匹配），
如仍有差异，用 `tests/test_main_args.py` 里 `_is_ci()` 的思路把环境变量显式清掉：

```python
for key in main.CI_ENV_KEYS:
    monkeypatch.delenv(key, raising=False)
```

### Q5 能不能只跑「我改动的模块」的测试？

可以，但**提交前必须跑全量**（10 秒，没有成本）：

```bash
python -m pytest tests/test_utils_excelutil.py -q     # 快速迭代
python -m pytest tests -q                             # 提交前
```
