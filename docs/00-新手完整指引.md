# 新手完整指引（从看懂框架到接入 CI）

> **本文是给第一次接手这个项目的人看的唯一入口。**
> 一份文档走完五件事：**看哪 → 写用例 → 跑用例 → 接 Jenkins → 接 CI/CD**。
> 每一节末尾都给了「想更深入读哪份文档」，不用一开始就读完全部。

## 一、先建立心智模型（3 分钟）

### 1.1 这个框架在干什么

一句话：**用表格/文件存用例，用 pytest 跑接口，产出 Allure 报告。**

```
        用例数据                     执行逻辑                       被测系统
  ┌──────────────────┐      ┌──────────────────────┐      ┌──────────────────┐
  │ data/api_tables  │      │ testcase/  用例层     │      │  你的 web 系统    │
  │   .xlsx  (Excel) │─────▶│   test_*_driver.py   │      │  党政/财务/商城…  │
  │ data/cases/*.yaml│      │        │             │      │                  │
  │ MySQL 三张表      │      │        ▼             │      │                  │
  └──────────────────┘      │ api/  接口层 (PO)    │      └──────────────────┘
          数据源三选一        │   base_api.py  ★核心  │               ▲
          由 conf.ini 的     │        │             │               │
          data_source 决定   │        ▼             │      HTTP 请求  │
                            │ utils/requestsutil   │───────────────┘
                            │        │             │
                            │        ▼             │
                            │ common/ 参数化/关联/  │
                            │   认证/判定/断言      │
                            └──────────┬───────────┘
                                       ▼
                        Allure 报告 + 日志 + 结果回写
```

**三层理解这个框架**：

| 层 | 你只需要知道 |
| --- | --- |
| 数据 | 用例写在 Excel / YAML / MySQL 里，**加用例不用改代码** |
| 逻辑 | `api/base_api.py` 是唯一的执行核心，三种数据源共用它 |
| 差异 | 每个系统的认证/判定/编码差异，收在 `config/systems/*.ini` 一份档案里 |

### 1.2 ⚠️ 两个目录千万别搞混（新手第一大坑）

| 目录 | 测什么 | 需要内网吗 | 你什么时候碰它 |
| --- | --- | --- | --- |
| **`testcase/`** | **你的业务系统**（写用例在这里） | 需要 | **天天碰** |
| `tests/` | **框架自己**（离线自测） | 不需要 | 只在改了 `api/` `common/` `utils/` `config/` 后才碰 |

名字只差一个字母，职责完全相反。另外 `pytest.ini` 里写了 `testpaths = testcase`，
所以**裸执行 `pytest` 只会跑业务用例**；跑框架自测必须显式写 `pytest tests`。

## 二、从哪个文件开始看

### 2.1 顺序很重要：先跑通，再看代码

不要一上来就读 `api/base_api.py`（700 多行，会劝退）。
**先让它跑起来，带着"它是怎么跑的"这个问题去看代码，效率差 10 倍。**

```
第 1 步：按第三节跑通 python main.py          ← 先有体感
第 2 步：按 2.2 的顺序读代码                  ← 带问题读
第 3 步：按第四节加一条自己的用例             ← 立刻用上
第 4 步：按第六/七节接入 CI                   ← 产生价值
```

### 2.2 代码阅读顺序（9 步）

| # | 文件 | 看完你能回答 |
| --- | --- | --- |
| 1 | `main.py` | 入口是怎么起 pytest 的？`--smoke` 干了什么？ |
| 2 | `config/conf.ini` | 哪些配置可以改？（数据源、域名、报告…） |
| 3 | `config/settings.py` | 配置是怎么被读进来的？环境变量为什么能覆盖它？ |
| 4 | `testcase/test_excel_driver.py` | 表格里的一行，是怎么变成一个 pytest 用例的？ |
| 5 | **`api/base_api.py`** | ★ **核心**：请求、参数化、认证、关联、断言、生命周期全在这 |
| 6 | `common/base.py` | `${var}` 是怎么被替换掉的？`body.data.id` 这种路径怎么取值？ |
| 7 | `utils/requestsutil.py` | HTTP 请求最终是怎么发出去的？ |
| 8 | `utils/excelutil.py` | Excel 怎么读？结果怎么回写？为什么不是每条都存盘？ |
| 9 | `common/profile.py` | 换了系统，差异是怎么被"配置化"的？ |

> **重点**：看懂第 5 步的 `BaseApi` 的 6 个方法（`request` / `extract` /
> `check_*` / `run_case` / `paginate` / `assert_*`），这个框架对你就没有秘密了。

### 2.3 按角色选路线

| 你的角色 | 只需要读 | 可以跳过 |
| --- | --- | --- |
| 只想把用例跑起来 | 2.2 的 1~3 步 | 其余全部 |
| 要写/维护用例 | 2.2 的 1~8 步 + 第四节 | `common/auth.py`、`hooks.py` |
| 要接一个新的 web 系统 | 2.2 全部 + [08-系统适配指南](08-系统适配指南.md) | `tests/` |
| 要改框架代码 | 2.2 全部 + [03-框架设计](03-框架设计.md) + [07-单元测试](07-单元测试.md) | — |
| 要接流水线 | 第三节 + 第六/七节 + [06-CICD集成](06-CICD集成.md) | `common/`、`utils/` 细节 |

### 2.4 这些可以先不看

| 目录/文件 | 为什么可以先跳过 |
| --- | --- |
| `tests/` | 里面全是替身对象、monkeypatch 等**测试技巧**，不是框架设计。先读会把你带偏 |
| `legacy/` | 旧版本归档（重构前的原始脚本），不参与运行，可以直接删 |
| `common/auth.py` `response.py` `hooks.py` `asserts.py` | 只在**接新系统**时才需要，由 [08-系统适配指南](08-系统适配指南.md) 按「解决什么问题」组织，比按代码顺序读更好懂 |
| `venv/` | 已废弃（指向不存在的 Python 路径），不要用 |

> **不但不要跳过、反而强烈建议先看的两个**：
> - `tools/mock_server.py` —— 本地 mock 服务，让你在没有被测系统时也能完整跑通（见 3.2 步骤 3）
> - `examples/` —— 商城 / 数据中台 / 老系统三套对照示例，一眼看出「换系统只换档案」

## 三、环境准备与 5 分钟跑通

### 3.1 装什么

| 项 | 要求 | 说明 |
| --- | --- | --- |
| Python | 3.7+（建议 3.10+） | 必需 |
| 依赖包 | `pip install -r requirements.txt` | 必需 |
| Java + allure CLI | 2.29+ | **可选**，只为把结果渲染成 Allure HTML；不装也能跑测试 |

```bash
cd amsapi-auto
python -m venv venv && venv\Scripts\activate        # Windows，推荐用虚拟环境
pip install -r requirements.txt
```

### 3.2 五步跑通

**步骤 1｜确认配置**（`config/conf.ini`）——新人只需要看这四项：

```ini
[env]
base_url =                    ; 留空 = 用例自己写全 url
system   = default            ; 系统适配档案；接别的系统才改（见 08）

[run]
data_source = excel           ; 先用 excel 上手
write_back  = true            ; 本地跑建议 true（把结果写回表格）

[report]
report_type = allure
```

**步骤 2｜先跑框架自测**（离线，约 10 秒，不连内网）：

```bash
python -m pytest tests -q
```

看到 `1118 passed, 16 skipped` 之类 = 本地环境完整。

> `16 skipped` 是**正常的**：其中 15 条依赖可选包（`jsonschema` / `cryptography`）、
> 1 条需要当前目录是 git 仓库。装上可选包后变 `1133 passed`，不装就自动跳过 —— 这是设计约定，不是报错。

**步骤 2.5｜执行前先体检环境（可选，但强烈建议）**：

```bash
python tools/preflight.py     # 依赖 / 配置 / 用例数据 / 可写目录 / 目标连通性，一次看清
```

出现「错误」先按提示修；「警告」多为可选依赖未装，不影响执行。

**步骤 3｜起本地 mock 服务（手里没有可访问的被测系统时，必做这一步）**：

```bash
# 终端 A：保持开着。它把示例接口在你本机复刻出来，不连内网也不连外网
python tools/mock_server.py
```

**步骤 4｜跑业务用例**：

```bash
python main.py --collect-only     # 先只收集不执行（完全只读），确认用例被读到

# 没连内网：把域名指向本地 mock 后再跑（终端 B）
AMSAPI_BASE_URL=http://127.0.0.1:18080 AMSAPI_DATA_SOURCE=yaml python main.py

# 已连被测环境：直接跑
python main.py
```

**步骤 5｜看报告与日志**：

```bash
python tools/generate_report.py --open
ls log/            # 日志按天存放，当天是 log/2026_09_27.log
```

> 完整的离线体验（含每条用例验证了什么、Excel 与 YAML 两种数据源、
> 以及商城 / 中台 / 老系统三套对照示例）见
> [操作手册 · 2.6 不连内网也能跑通](02-操作手册.md#26-不连内网也能跑通离线体验)。

## 四、怎么编写用例

> **第一次写？直接抄模板**：[`examples/template/`](../examples/template/README.md)
> 里有 Excel 与 YAML 各一份填空式模板，复制改数就能跑；逐列讲解见
> [09-用例编写模板](09-用例编写模板.md)。下面这节讲「为什么这么写」。

### 4.1 四种方式怎么选

| 方式 | 位置 | 适合 | 不适合 | 上手难度 |
| --- | --- | --- | --- | --- |
| **Excel** | `data/api_tables.xlsx` | 业务同学维护、用例多且同构 | 需要复杂嵌套结构 | ★ |
| **YAML** | `data/cases/*.yaml` | 开发维护、需要 diff | 非技术人员维护 | ★★ |
| **MySQL** | 数据库三张表 | 多系统共用、集中管理 | 快速迭代阶段 | ★★★ |
| **手写 pytest** | `testcase/test_xxx.py` | 多接口串联、分支断言 | 同构的简单校验 | ★★★ |

> **新人的建议路径**：先用 Excel 加一条最简单的 → 会了再试 YAML → 流程复杂了才手写。
> 三种数据源的**字段完全一致**，学会一种就会另外两种。

### 4.2 方式一：Excel 用例（最常用）

**文件**：`data/api_tables.xlsx` → 工作表 `test_case_list`

#### 列含义（当前示例文件是 A~V 共 22 列）

| 列 | 字段 | 必填 | 说明 |
| --- | --- | --- | --- |
| A | `id` | **是** | 用例编号。用于报告标题、`depends` 依赖、单条执行 |
| B | `time` | — | **框架自动回写**，别手工填 |
| C | `title` | **是** | 用例标题，显示在报告里 |
| D | `url` | **是** | 接口地址。推荐写**相对路径**（如 `/v1/users/login`），由 `base_url` 或系统档案补域名；也支持 `${var}` |
| E | `method` | **是** | `get` / `post` / `put` / `patch` / `delete` / `head` / `options` |
| F | `headers` | 否 | **JSON 字符串**，如 `{"Content-Type": "application/json"}`，支持 `${var}` |
| G | `cookies` | 否 | JSON 字符串 |
| H | `request_body` | 否 | 请求体，JSON 字符串，支持 `${var}` |
| I | `request_type` | 否 | 请求体类型（兼容旧列；新增列 `content_type` 优先） |
| J | `relation` | 否 | 关联提取，如 `ticket=body.data.ticket`，多个用逗号分隔 |
| K | `expected_code` | 否 | 期望业务码。**是否必填取决于系统档案**：`status`/`code` 风格必填，`success`/`errno` 风格可留空 |
| L | `response` | — | **框架自动回写** |
| M | `ispass` | — | **框架自动回写** |
| N | `isdel` | **是** | `1` = 执行；其它值或留空 = 跳过 |
| O | `tags` | 否 | 标签，多个用逗号分隔（如 `smoke`、`smoke,core`）。用于 CI 冒烟筛选 |
| P | `host` | 否 | 域名别名，对应系统档案 `[hosts]` 段（网关 + 多服务系统） |
| Q | `content_type` | 否 | 覆盖默认请求体类型 |
| R | `expects` | 否 | 字段级断言，如 `gt:body.total=0; not_empty:body.rows` |
| S | `setup` | 否 | 前置步骤（造数据），JSON 数组 |
| T | `teardown` | 否 | 后置清理，JSON 数组；**断言失败也会执行** |
| U | `depends` | 否 | 依赖的用例 id，逗号分隔；前置未通过则本用例**跳过而非失败** |
| V | `check_business` | 否 | 是否做业务码断言，默认做；令牌 / 下载类接口可填 `0` |

> **P~V 是可选列**：老用例表只有 A~O 共 15 列也照常运行；
> 当前示例文件把它们都加上了，方便你对照着抄。

**仓库现有 5 条示例用例**（配 `tools/mock_server.py` 可离线跑通）：

| id | title | url | method | relation / depends | expected_code | tags |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 登录并提取票据 | `/v1/users/login` | get | `ticket=body.data.ticket` | 200 | smoke |
| 2 | 按 id 查询字典 | `/dicts` | get | | 200 | smoke |
| 3 | 查询权限点（携带票据） | `/admin/resource/authority` | get | `depends=1` | 200 | smoke |
| 4 | 分页查询组织树 | `/admin/org/getTreeRootParentCodePage` | get | `depends=1` | 200 | |
| 5 | 依赖未满足会被跳过（depends 演示） | `/admin/resource/authority` | get | `depends=99`（不存在）→ 跳过 | 200 | |

> url 全部用**相对路径**：真实域名由 `AMSAPI_BASE_URL` 或系统档案提供，
> 因此同一份用例可在测试 / 预发 / 生产之间切换，不用改数据。
>
> 想实际看到它们跑通，看 [操作手册 · 2.6 不连内网也能跑通](02-操作手册.md#26-不连内网也能跑通离线体验)。

#### 手把手：新增一条用例

1. 打开 `data/api_tables.xlsx` → `test_case_list`
2. 在**最后一行下面**新增一行
3. 至少填 **A、C、D、E、K、N** 六列：
   ```
   A6: 6
   C6: 查询商品列表
   D6: /v1/goods
   E6: get
   K6: 200
   N6: 1
   ```
4. 保存（**必须保存后再跑**，框架每次执行时读文件）
5. 确认被读到：
   ```bash
   python main.py --collect-only
   ```
   > 输出里应能看到 `id6[查询商品列表]`
6. 单条执行验证：
   ```bash
   python main.py -k "id6"
   ```

#### 格式坑（照这个表写，能避开 90% 的问题）

| 场景 | 正确 | 错误 |
| --- | --- | --- |
| `headers` 为空 | 留空 或 `{}` | 写 `None`（会被当字符串） |
| 引用变量 | `{"access-ticket": "${ticket}"}` | `{"access-ticket": "$ticket"}`（少花括号） |
| 关联多个变量 | `a=body.data.a,b=body.data.b` | 用换行分隔 |
| 数字型字段 | `{"page": 1}` | `{"page": "1"}`（类型不符可能被拒） |
| 多个标签 | `smoke,core` | 用顿号分隔（能解析但不推荐） |
| 期望值本身带 `=` | `equals:body.a=1=2`（只按第一个 `=` 切） | — |

> 框架用 `safe_loads()` 解析，**同时兼容 JSON 与 Python 字面量**（单引号也能跑），
> 但仍**推荐写 JSON**，因为 YAML/MySQL 数据源与工具链都按 JSON 标准工作。

#### ⚠️ 执行顺序 = 行序

**Excel 的行顺序就是执行顺序**。所以：
登录用例（提取 `ticket`）**必须排在**依赖 `ticket` 的用例**前面**。
要调顺序，直接挪行。

### 4.3 方式二：YAML 用例

**位置**：`data/cases/`，一个业务模块一个文件。仓库现有 `login.yaml`、`dict.yaml`、`admin.yaml`。

**完整示例**（照抄 `data/cases/login.yaml` 的结构）：

```yaml
# 登录模块用例
# relation 提取出的 ticket 会写入全局变量池，供后续用例以 ${ticket} 引用
cases:
  - title: 登录系统
    tags: [ smoke ]                              # 参与冒烟测试
    url: http://192.0.2.10:9050/v1/users/login
    method: get
    headers: { "Content-Type": "application/json" }
    cookies: { }
    request_body:
      username: demo_user
      password: demo_password_hash
      sign: demo_sign_value
    relation: ticket=body.data.ticket            # ★ 提取 ticket 给后续用例用
    expected_code: 200
    isdel: 1
```

**两种文件结构都支持**（二选一，不要混用）：

```yaml
# 形式一：带 cases 键
cases:
  - title: xxx
    ...

# 形式二：文件本身就是列表
- title: xxx
  ...
```

**字段与 Excel 完全一致**，只是换成 YAML 语法。**必须注意**：

| 项 | 说明 |
| --- | --- |
| 编码 | 必须 UTF-8，否则中文乱码 |
| 缩进 | 统一 2 空格，**绝对不要用 Tab** |
| `isdel` | 不写默认 `1`（参与执行） |
| 回写 | YAML 用例**不回写**执行结果 |
| `expected_code` 不写 | **判失败**（fail-closed）。`status` / `code` 风格必须给期望值；不做业务断言请写 `check_business: false` |
| 加载顺序 | **按文件名升序**。依赖 `${ticket}` 的用例，其登录文件要命名靠前（如 `01-login.yaml`） |

**验证**：

```bash
python main.py --collect-only | grep 商品     # 确认被读到
python main.py -m yaml                       # 只跑 YAML 数据源
```

### 4.5 方式四：手写 pytest 用例（流程复杂时用）

数据驱动适合"同构的简单用例"。**多接口串联、有分支判断**时，手写更清晰。

```python
# -*- coding: utf-8 -*-
"""登录 -> 提取 ticket -> 查询权限点"""
import allure
import pytest

from api.login_api import LoginApi
from api.admin_api import AdminApi

USERNAME = "demo_user"
PASSWORD = "demo_password_hash"
SIGN = "demo_sign_value"


@allure.epic("接口自动化")
@allure.feature("PO 风格用例")
@pytest.mark.network                      # 依赖真实环境，可 -m "not network" 跳过
class TestLoginFlow:

    @allure.story("登录流程")
    @allure.title("登录 -> 提取 ticket -> 查询权限点")
    @allure.severity(allure.severity_level.CRITICAL)
    def test_login_and_use_ticket(self):
        # 1) 登录：ticket 自动写入全局变量池
        with allure.step("登录并提取 ticket"):
            login = LoginApi()
            ticket = login.login_and_save_ticket(USERNAME, PASSWORD, SIGN)
            login.check_status(200)               # HTTP 状态码断言
            login.check_business_code(200)        # 业务状态码断言
            assert ticket, "登录成功但未提取到 ticket"

        # 2) 用 ticket 访问权限接口
        with allure.step("携带 ticket 查询权限点"):
            admin = AdminApi()
            admin.get_authority_with_ticket("demo-app", username=USERNAME)
            admin.check_business_code(200)
            admin.check_json("body.status", 200)  # 路径根是"完整响应"，故带 body. 前缀
```

**四条规范**：

1. 每个关键动作包一个 `with allure.step(...)` → 报告里形成步骤树
2. 断言用 `check_*` / `assert_*` 方法
3. 依赖真实环境的用例打 `@pytest.mark.network`
4. 要参与 CI 冒烟的用例打 `@pytest.mark.smoke`

> 参考实现：`testcase/test_login.py`（本文件就是从这个真实文件简化的）。

**需要新增接口对象时**（如订单模块）→ 新建 `api/order_api.py`，
**只封装"怎么调"，不写断言**。完整模板见 [04-开发指南 · 新增接口对象](04-开发指南.md#一新增接口对象)。

### 4.6 参数关联：`ticket` 到底是怎么传下去的 ★

这是本框架最有价值、也是新手最容易懵的机制。

```
① 用例 1「登录系统」的 relation 列填写：   ticket=body.data.ticket
        │
        ▼
② 框架执行完登录后，按路径 body → data → ticket 取值，写入全局变量池 GlobalVar
        │
        ▼
③ 用例 5 的 request_body 里写：  {"access-ticket": "${ticket}"}
        │
        ▼
④ 请求发出前，框架把 ${ticket} 替换成真实值
```

**三个必须记住的点**：

| 点 | 说明 |
| --- | --- |
| **路径根是「完整响应」** | 所以响应体字段**必须写 `body.` 前缀**。写成 `data.ticket` 会取到 `None` ← 最常见错误 |
| 支持列表下标 | `first=body.data.rows.0.name`（用 `.0`，**不支持** `[0]`） |
| 多个关联 | 逗号分隔：`ticket=body.data.ticket,uid=body.data.user.id` |

### 4.7 断言怎么写

**三层断言**，一般只写第一条就够：

| 方法 | 断言对象 | 说明 |
| --- | --- | --- |
| `check_success(expected)` | **业务是否成功** | 规则来自系统档案，**换系统不用改用例**（推荐） |
| `check_status(code)` | HTTP 状态码 | |
| `check_business_code(code)` | 业务码（固定 `body.status`） | 兼容存量用例 |
| `check_json(path, expected)` | 任意 JSON 路径的值 | 根为完整响应 |

**字段级断言**有 21 种算子，在数据里配 `expects` 即可，**不用写代码**：

```yaml
# YAML 写法（结构化）
expects:
  - op: not_empty
    path: body.data.items
  - op: gt
    path: body.data.total
    value: 0
  - op: elapsed
    value: 3000
```

```
Excel 写法（P~V 可选扩展列里的 expects 一列写完）
not_empty:body.data.items; gt:body.data.total=0; elapsed=3000
```

算子清单：`equals` `not_equals` `contains` `not_contains` `startswith` `endswith`
`regex` `type` `exists` `not_exists` `in` `not_in` `gt` `ge` `lt` `le` `length`
`empty` `not_empty` `elapsed` `schema`。

## 五、怎么执行用例

### 5.1 最常用 5 条

```bash
python main.py                      # 跑全部用例（按 conf.ini 配置）
python main.py --smoke              # ★ 只跑冒烟用例（CI 构建后验证）
python main.py --collect-only       # 只收集不执行（完全只读，排错第一步）
python main.py -k login             # 只跑名称含 login 的用例
python main.py --report none        # 不生成报告，快速回归
```

### 5.2 筛选

```bash
python main.py -m excel             # 只跑 Excel 数据源
python main.py -m yaml              # 只跑 YAML 数据源
python main.py -m mysql             # 只跑 MySQL 数据源
python main.py -m "not network"     # 跳过依赖真实环境的用例
python main.py -k "id6"             # 按用例名/编号筛
python main.py --smoke -m excel     # 可以组合：冒烟 + 只看 Excel
```

**可用 marker**：`smoke`、`excel`、`yaml`、`mysql`、`network`

### 5.3 报告与日志

| 产物 | 位置 | 说明 |
| --- | --- | --- |
| Allure 原始数据 | `report/allure-results/` | 每次都生成 |
| Allure HTML | `report/allure-report/index.html` | 需 allure CLI 渲染 |
| pytest-html | `report/report.html` | `--report html` 时生成 |
| 日志 | `log/YYYY_MM_DD.log` | 含每次请求的 headers / body / 响应；**按大小轮转 + 按天保留** |

```bash
python tools/generate_report.py --open    # 渲染并打开 Allure HTML
```

> **不要双击 `index.html` 打开** —— AJAX 会被 `file://` 安全策略拦截，页面空白。
> 用 `allure open` 或上面的命令。

**两件你会看到、但不要误会的事**：

| 现象 | 说明 |
| --- | --- |
| 日志/报告里口令变成 `dem****rd` | **脱敏默认开启**，是保护机制生效，不是用例写错。需看原文用 `AMSAPI_MASK_SENSITIVE=false`（仅本地调试） |
| Allure「环境」页多了运行位置 / Python 与依赖版本（git 提交、构建号**有则显示**） | **执行元数据**，用来回答「这份报告对应哪次提交、跑了什么版本」 |

> 会话最后若打印 **`teardown 汇总`** 告警，说明有用例的清理步骤失败（可能留下脏数据），
> 按告警里的 case_id 到日志里搜 `teardown 失败` 看上下文。

### 5.4 退出码（CI 判定依据）

| 退出码 | 含义 | 流水线处理 |
| --- | --- | --- |
| `0` | 全部通过 | 放行 |
| `1` | 有用例失败 | **中断流水线** |
| `2` | 参数错误 | 中断，检查配置 |
| `5` | 没收集到任何用例 | 中断，检查筛选条件与用例数据 |

> 退出码就是 pytest 退出码，**不需要额外解析输出**。
> `5` 通常意味着筛选条件写错或用例全被 `isdel` 跳过，**也要当成失败**。

## 六、怎么接入 Jenkins

### 6.1 三步接入

| 步骤 | 操作 |
| --- | --- |
| **1. 装插件** | Jenkins → 系统管理 → 插件管理 → 安装 **Allure Jenkins Plugin** 与 **Pipeline** |
| **2. 建任务** | 新建任务 → 选 **Pipeline** → 定义选 **Pipeline script from SCM** → 脚本路径填 **`Jenkinsfile`** → 保存 |
| **3. 构建** | 直接点「立即构建」，或在构建时填参数（域名/环境/系统档案） |

仓库根目录的 **`Jenkinsfile` 已经写好了**，不用自己从零编。

### 6.2 流水线做了什么

```
检出代码 → 准备环境（装依赖 + 注入参数） → 数据与配置自检（只读）
        → 框架单元测试（离线 4 秒） → 冒烟测试 / 全量回归 → 归档日志 + Allure 报告
```

| 阶段 | 命令 | 作用 |
| --- | --- | --- |
| 数据与配置自检 | `python main.py --collect-only` | 完全只读，确认用例能被读到 |
| **框架单元测试** | `python -m pytest tests -q` | 离线 4 秒，验证**框架自身**没被改坏 |
| 冒烟测试 | `python main.py --smoke --report allure` | `RUN_MODE=smoke` 时执行 |
| 全量回归 | `python main.py --report allure` | `RUN_MODE=full` 时执行 |

> **为什么单元测试放在接口测试前面？**
> 它验证的是"测试工具本身"。工具坏了，后面接口测试的结果全是噪音，
> 所以先失败先止，避免浪费时间排查假问题。

### 6.3 构建参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `RUN_MODE` | `smoke` | `smoke` 只跑冒烟（快）；`full` 全量回归 |
| `TARGET_ENV` | `test` | 环境标识（`test`/`uat`/`prod`），写入报告「环境」页 |
| `BASE_URL` | 空 | 接口域名。**留空用仓库配置；填写则覆盖** |
| `SYSTEM` | `default` | 系统适配档案名。**换被测系统只改这一项** |
| `SMOKE_TAGS` | `smoke` | 冒烟标签，可改成 `core` 等 |
| `WRITE_BACK` | `false` | 是否回写数据源。**CI 保持 false** |
| `TIMEOUT` | `30` | 请求超时（秒） |
| `DATA_SOURCE` | `excel` | 用例数据源 |

> **为什么 CI 里 `WRITE_BACK` 必须是 `false`？**
> 回写会改动仓库里的 `api_tables.xlsx`，导致工作区变脏、并发构建互相覆盖。
> 结果看 Allure 报告就够了。

### 6.4 部署后自动触发冒烟（最关心的场景）

**方式一：上游部署 Job 触发下游（推荐）**

在**部署 Job** 的末尾加：

```groovy
stage('部署后触发冒烟') {
    steps {
        build job: 'amsapi-auto-smoke',              // 冒烟 Job 名
              parameters: [
                  string(name: 'BASE_URL',   value: 'https://api.example.com'),
                  string(name: 'TARGET_ENV', value: 'uat'),
                  string(name: 'RUN_MODE',   value: 'smoke')
              ],
              wait: true,                            // 等待冒烟结果
              propagate: true                        // 冒烟失败 → 部署也标记失败
    }
}
```

`wait: true` + `propagate: true` 是关键：**冒烟失败会拦截问题版本继续流向下一环境**。

**方式二：同一个 Jenkinsfile 里串联**

```groovy
stage('部署')     { steps { sh './deploy.sh' } }
stage('冒烟测试') { steps { sh 'python main.py --smoke --report allure' } }
```

**方式三：构建触发器**

任务配置 → 构建触发器 → 勾选 **Build after other projects are built** → 填部署 Job 名。

### 6.5 定时全量回归

任务配置 → 构建触发器 → **Build periodically**：

```
H 2 * * *        # 每天凌晨 2 点左右跑一次，配合 RUN_MODE=full
```

### 6.6 推荐的 Job 划分

| Job | 触发方式 | 参数 | 用途 |
| --- | --- | --- | --- |
| `amsapi-auto-smoke` | 部署后触发 / 手动 | `RUN_MODE=smoke` | 部署验证，几十秒出结果 |
| `amsapi-auto-full` | 定时（每日）+ 手动 | `RUN_MODE=full` | 全量回归 |

### 6.7 排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `python: command not found` | 节点没有 Python | 节点装 Python 或用容器 |
| 单元测试阶段失败 | 框架代码被改坏 | 本地 `python -m pytest tests -x --tb=long` |
| 冒烟收集 0 条（退出码 5） | 没有用例带 `smoke` 标签 | 检查 Excel `tags` 列 / YAML `tags` 字段 |
| 全部连接失败 | `BASE_URL` 没注入，还在连测试地址 | 看构建日志开头的「全局域名」 |
| 报告页没有 Allure 入口 | 没装插件，或 `allure-results` 为空 | 装插件；确认没加 `--report none` |
| 每次构建都很慢 | 在 CI 里做了本地 HTML 渲染 | 确认启动摘要显示 `CI 环境: 是` |
| 工作区出现 `api_tables.xlsx` 变更 | `write_back` 是 true | 设 `AMSAPI_WRITE_BACK=false` |

**排查三板斧**：

1. 看构建日志开头的**启动摘要**（环境/模式/数据源/CI 判定）是否与预期一致
2. `python main.py --collect-only` 确认收集到的用例对不对（只读）
3. 下载归档的 `log/*.log`，搜 `【请求】`、`【关联】`、`请求异常`

## 七、怎么接入 CI/CD 流水线

### 7.1 三条通用原则

| 原则 | 做法 |
| --- | --- |
| **不改仓库文件切环境** | 用 `AMSAPI_*` 环境变量覆盖（优先级高于 `conf.ini`） |
| **不在 CI 回写数据** | `AMSAPI_WRITE_BACK=false` |
| **不在仓库放密码** | 用 Jenkins Credentials / GitLab CI Variables / GitHub Secrets 注入 |

### 7.2 环境变量速查（CI 用这套）

```bash
AMSAPI_ENV=uat \
AMSAPI_BASE_URL=https://api.example.com \
AMSAPI_SYSTEM=mall \
AMSAPI_WRITE_BACK=false \
AMSAPI_TIMEOUT=30 \
python main.py --smoke --report allure
```

| 变量 | 对应配置 | 示例 |
| --- | --- | --- |
| `AMSAPI_ENV` | 环境标识 | `uat` |
| `AMSAPI_BASE_URL` | 全局域名 | `https://api.example.com` |
| **`AMSAPI_SYSTEM`** | **系统适配档案** | `mall` / `finance_erp` |
| `AMSAPI_DATA_SOURCE` | 数据源 | `excel` / `yaml` / `mysql` |
| `AMSAPI_WRITE_BACK` | 是否回写 | `false` |
| `AMSAPI_TIMEOUT` | 请求超时 | `30` |
| `AMSAPI_REPORT_TYPE` | 报告类型 | `allure` |
| `AMSAPI_SMOKE` / `AMSAPI_TAGS` | 冒烟开关 / 标签 | `true` / `smoke` |
| `AMSAPI_CONF_FILE` | 指定配置文件 | `config/conf.ci.ini` |
| `AMSAPI_RENDER_ALLURE` | 强制本地渲染 HTML | `1` |

> **空字符串不覆盖**：`AMSAPI_BASE_URL=` 会被忽略，不会把配置清空，
> 避免 CI 中未填的参数意外破坏配置。
>
> **完整清单**（含数据库类、目录类变量）见
> [06-CICD集成 · 环境变量覆盖](06-CICD集成.md#三环境变量覆盖ci-的关键能力)。

### 7.3 GitLab CI

仓库根目录新建 `.gitlab-ci.yml`：

```yaml
stages:
  - unit
  - test

variables:
  AMSAPI_REPORT_TYPE: allure
  AMSAPI_WRITE_BACK: "false"          # YAML 里布尔要加引号，否则被解析成 bool
  AMSAPI_TIMEOUT: "30"

# 框架单元测试：离线自检，任何变更都先跑（约 10 秒）
unit-test:
  stage: unit
  image: python:3.10
  script:
    - pip install -r requirements.txt
    - python -m pytest tests -q

# 冒烟测试：合并请求 / 手动触发时执行
smoke-test:
  stage: test
  image: python:3.10
  needs: ["unit-test"]                      # 框架自检通过才跑接口测试
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_PIPELINE_SOURCE == "web"
  script:
    - pip install -r requirements.txt
    - python main.py --smoke --report allure
  artifacts:
    when: always                             # 失败也要保留产物，便于排查
    paths:
      - report/allure-results/
      - log/
    expire_in: 1 week

# 全量回归：定时执行
full-regression:
  stage: test
  image: python:3.10
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
  script:
    - pip install -r requirements.txt
    - python main.py --report allure
  artifacts:
    when: always
    paths:
      - report/allure-results/
      - log/
    expire_in: 1 week
```

**部署后自动触发**（在部署项目的 `.gitlab-ci.yml` 里）：

```yaml

  trigger:
    project: your-group/amsapi-auto
    strategy: depend            # 等待冒烟结果，失败则本流水线失败
```

### 7.4 GitHub Actions

新建 `.github/workflows/api-smoke.yml`：

```yaml
name: API Smoke Test

on:
  workflow_run:
    workflows: ["Deploy"]        # 部署工作流完成后自动触发
    types: [completed]
  workflow_dispatch:             # 支持手动触发

jobs:
  smoke:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.10'

      - name: 安装依赖
        run: pip install -r requirements.txt

      - name: 框架单元测试
        run: python -m pytest tests -q

      - name: 执行冒烟测试
        env:
          AMSAPI_ENV: uat
          AMSAPI_BASE_URL: https://api.example.com
          AMSAPI_WRITE_BACK: "false"
          AMSAPI_TIMEOUT: "30"
        run: python main.py --smoke --report allure

      - name: 上传报告数据
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: allure-results
          path: report/allure-results/
```

### 7.5 CI 下的自动优化

框架检测到 CI 环境（`JENKINS_URL` / `GITLAB_CI` / `GITHUB_ACTIONS` / `CI` 等）会**自动跳过本地 HTML 渲染**，
只产出 `report/allure-results/`，交给流水线的 Allure 插件渲染 —— 显著缩短构建时长。
启动摘要里会显示 `CI 环境: 是`，可据此确认参数注入成功。

### 7.6 本地开发 vs CI 的配置差异

| 配置 | 本地开发 | CI 冒烟 | CI 全量 |
| --- | --- | --- | --- |
| `write_back` | `true` | `false` | `false` |
| `timeout` | `10` | `30` | `30` |
| `smoke` | `false` | `true` | `false` |
| 本地 HTML 渲染 | 是 | 否（插件渲染） | 否 |

## 八、新人最容易踩的 10 个坑

| # | 坑 | 正确做法 |
| --- | --- | --- |
| 1 | 把用例写到 `tests/` 里 | 写用例去 **`testcase/`**；`tests/` 只测框架自身 |
| 2 | 关联路径写成 `data.ticket` | 必须写 `body.data.ticket`（**路径根是完整响应**） |
| 3 | 变量写成 `$ticket` | 必须写 `${ticket}`（带花括号） |
| 4 | Excel 改了没保存就执行 | **保存后再跑**，框架每次读文件 |
| 5 | 登录用例排在依赖它的用例后面 | Excel 按**行序**执行；YAML 按**文件名升序**，登录文件命名靠前 |
| 6 | YAML 里用了 Tab 缩进 | 统一 2 空格 |
| 7 | CI 里 `write_back=true` | 设 `AMSAPI_WRITE_BACK=false` |
| 8 | 双击 `allure-report/index.html` 打开空白 | 用 `python tools/generate_report.py --open` |
| 9 | 看到日志里 `dem****rd` 以为用例写错了 | 那是**脱敏生效**；要看原文设 `AMSAPI_MASK_SENSITIVE=false`（仅本地） |
| 10 | 内网/`127.0.0.1` 请求报 502，以为服务挂了 | 企业环境注入了 `HTTP_PROXY`；框架已自动对内网地址绕过代理，仍不通就设 `AMSAPI_TRUST_ENV=false` |

## 九、第一天 Checklist

按顺序做完，你就完全接手了：

## 十、速查卡（打印贴墙用）

```bash
# ========== 框架自测（离线，改框架代码后必跑）==========
python -m pytest tests -q
python -m flake8 .                     # 风格检查（改过代码就跑）

# ========== 执行前体检（环境问题与业务失败分开）==========
python tools/preflight.py
AMSAPI_BASE_URL=http://127.0.0.1:18080 python tools/preflight.py   # 连本地 mock

# ========== 执行用例 ==========
python main.py                         # 全量
python main.py --smoke                 # 只跑冒烟
python main.py --collect-only          # 只收集不执行（只读，排错第一步）
python main.py -k "id6"                # 只跑 id6
python main.py -m yaml                 # 只跑 YAML 数据源
python main.py -m "not network"        # 跳过真实环境用例
python main.py --report none           # 不产报告，快速回归

# ========== 报告与日志 ==========
python tools/generate_report.py --open
ls log/

# ========== 换环境 / 换系统（不改仓库文件）==========
AMSAPI_BASE_URL=https://api.example.com python main.py --smoke
AMSAPI_SYSTEM=mall python main.py --smoke
AMSAPI_MASK_SENSITIVE=false python main.py -k id1     # 临时看未脱敏原文（仅本地）
AMSAPI_TRUST_ENV=false python main.py       # 内网专线：完全不读系统代理

# ========== CI 常用 ==========
AMSAPI_ENV=uat AMSAPI_BASE_URL=https://api.example.com \
AMSAPI_WRITE_BACK=false AMSAPI_TIMEOUT=30 \
python main.py --smoke --report allure
```

**三处最常改的地方**：

| 想改什么 | 改哪 |
| --- | --- |
| 环境 / 数据源 / 报告类型 | `config/conf.ini` |
| 接一个新的 web 系统 | `config/systems/<系统>.ini`（+ `conf.ini` 的 `system`） |
| 加用例 | `data/api_tables.xlsx` 或 `data/cases/*.yaml` |
