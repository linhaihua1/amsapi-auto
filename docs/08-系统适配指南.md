# 系统适配指南（一套框架跑通各类 web 系统）

> 面向：需要把本框架接到**党政/政务、财务/ERP、商城/购物、数据中台/信息系统**等
> 不同风格 web 系统上的人。
> 目标：**换一个被测系统，只改一份档案文件（或一个环境变量），用例数据不用改、框架代码不用改。**

---

## 一、为什么需要「系统适配」

原来的框架把两件事写死在代码里：

```python
# 旧写法（写死）
assert res["body"]["status"] == 200          # 业务成功 = body.status == 200
headers["access-ticket"] = GlobalVar.get("ticket")   # 认证 = 固定头名
```

这在一个自研系统里没问题，但换成别的系统就会**全线失败**——不是因为业务有 bug，
而是因为对方的约定不一样。真实差异其实只有固定的那么几处：

| # | 差异点 | 党政/政务 | 财务/ERP | 商城/购物 | 数据中台/信息系统 |
| --- | --- | --- | --- | --- | --- |
| 1 | 成功怎么判 | `body.status == 200` | `body.code == 0/200` | `body.success == true` | `body.errno == 0` |
| 2 | 业务码字段名 | `status` | `code` / `resultCode` | `success` / `ok` | `errno` / `retCode` |
| 3 | 令牌放哪 | 自定义头 `access-ticket` | Cookie / `Token` 头 | `Authorization: Bearer` | `Authorization: Bearer` |
| 4 | 令牌怎么来 | 登录接口返回 | 会话 Cookie | 登录接口返回 JWT | OAuth2 自动取 |
| 5 | 请求体格式 | JSON | 表单 `x-www-form-urlencoded` | JSON | JSON / XML |
| 6 | 响应格式 | JSON | JSON / XML | JSON | JSON / XML |
| 7 | 字符编码 | UTF-8 / GBK | GBK / GB2312 | UTF-8 | UTF-8 |
| 8 | 域名结构 | 单一域名 | 单一域名 | 多域名（主站/商品/订单） | 网关 + 多个微服务 |
| 9 | 签名 | 少数有 | 普遍有（md5 + 盐 + 排序） | 普遍有 | 常见 |
| 10 | 时间戳防重放 | 有 | 有 | 有 | 有 |
| 11 | 报文加解密 | 少见 | 常见（AES/国密） | 少见 | 常见 |
| 12 | 错误消息字段 | `msg` | `message` / `errmsg` | `msg` | `errmsg` / `retMsg` |

**结论**：把 1–12 这些差异从代码里抽出来，放进一份声明式档案，换系统就只是换档案。
这就是 `common/profile.py`（系统适配档案层）要做的事。

> 不想用适配（或只有一个老系统）时**什么都不用配**：框架默认使用内置 `default` 档案，
> 行为与改造前**完全一致**。这是刻意的设计——存量用例零迁移成本。

## 二、30 秒上手

假设要把框架接到一个「商城系统」，它的特点是 `{"success": true}` 判定成功、
令牌走 `Authorization: Bearer`：

```bash
# 1. 看一眼有哪些现成档案
ls config/systems/
#   default.ini  gov.ini  finance_erp.ini  mall.ini  dataplatform.ini

# 2. 用现成的商城档案跑（本地跑）
AMSAPI_SYSTEM=mall python main.py --smoke

# 或者写进配置，长期生效
#   config/conf.ini →  [env] system = mall
```

就这样，**用例数据一行都不用改**。

如果现成档案不完全匹配（比如商城用的不是 `success` 而是 `errno`），
复制一份改几行即可：

```bash
cp config/systems/mall.ini config/systems/mall2.ini
# 编辑 mall2.ini 的 [response] 段：style = errno
AMSAPI_SYSTEM=mall2 python main.py
```

## 三、档案在哪里、怎么切

### 3.1 位置与文件格式

```
config/systems/
├── default.ini          内置默认（无文件也可用，等价改造前行为）
├── gov.ini      党政 / 政务
├── finance_erp.ini      财务 / ERP
├── mall.ini             商城 / 购物
└── dataplatform.ini     数据中台 / 信息系统
```

档案就是一份普通 `.ini`，用 `[段]` 组织。**档案名 = 文件名去掉 `.ini`**。

> 也可以把档案放在任意目录，用 `AMSAPI_SYSTEMS_DIR=/path/to/systems` 整体重定向
> （CI 里想用另一批档案时很有用）。

### 3.2 三种切换方式与优先级

| 优先级 | 方式 | 用法 | 适用场景 |
| --- | --- | --- | --- |
| 1（最高） | 环境变量 | `AMSAPI_SYSTEM=mall` | **CI/CD**（不改仓库文件） |
| 2 | 配置文件 | `conf.ini` 的 `[env] system = mall` | 本地长期切换 |
| 3 | 代码指定 | `load_profile("mall")` | 手写用例里临时指定 |

不指定 → 使用内置 `default` 档案。

档案名写错**不会静默降级**，会直接报错并列出可用档案：

```
ConfigError: 未找到系统适配档案 'mal'。
  期望文件：config/systems/mal.ini
  可用档案：gov, dataplatform, default, finance_erp, mall
```

### 3.3 档案是进程内缓存的

同一份档案只解析一次（避免每条用例都读盘）。改了档案文件后需要：

```bash
# 重启进程即可；单元测试里用 profile.clear_cache()
```

### 3.4 运行参数的三级优先级

只有「域名」和「超时/证书」走三级回退，因为它们是**环境属性**而不是**系统属性**：

| 参数 | 优先级（高 → 低） | 理由 |
| --- | --- | --- |
| 域名 | `AMSAPI_BASE_URL` / `conf.ini [env] base_url` > 档案 `[env] base_url` | 同一套用例要在测试/预发/生产之间切域名 |
| 超时 | `AMSAPI_TIMEOUT` > 档案 `[env] timeout` > `conf.ini [run] timeout` | 流水线可能要临时放宽超时 |
| 证书校验 | `AMSAPI_VERIFY` > 档案 `[env] verify` > `conf.ini [run] verify` | 内网自签证书场景 |
| 编码 / 报文格式 / 请求头 / 认证 / 响应判定 | 档案值 > 内置默认（**每一项都可用环境变量覆盖**，见 3.5） | 属于系统固有约定，默认不串环境 |

### 3.5 档案每一项都能被环境变量覆盖

档案的每个字段都有一一对应的环境变量 —— 也就是说**换环境可以完全不改档案文件**（CI 场景必需）：

| 档案位置 | 对应环境变量 | 示例 |
| --- | --- | --- |
| `[env] encoding` | `AMSAPI_ENCODING` | `AMSAPI_ENCODING=gbk` |
| `[env] content_type` | `AMSAPI_CONTENT_TYPE` | `AMSAPI_CONTENT_TYPE=application/xml` |
| `[env] response_format` | `AMSAPI_RESPONSE_FORMAT` | `AMSAPI_RESPONSE_FORMAT=xml` |
| `[hosts] <别名>` | `AMSAPI_HOST_<别名大写>` | `AMSAPI_HOST_ADMIN=https://admin.example.com` |
| `[auth] <字段>` | `AMSAPI_AUTH_<字段名大写>` | `AMSAPI_AUTH_CLIENT_SECRET=xxx`（CI 凭据） |
| `[hooks] before_request` | `AMSAPI_HOOKS_BEFORE_REQUEST` | `AMSAPI_HOOKS_BEFORE_REQUEST='common.hooks:make_sign_hook({...})'` |
| `[hooks] after_request` | `AMSAPI_HOOKS_AFTER_REQUEST` | 同上 |

约定：**空字符串视为「未设置」**，不会把档案里的值清空。

```bash
# 换域名 + 换编码 + 注入凭据，一行不改档案文件
AMSAPI_SYSTEM=finance_erp \
AMSAPI_BASE_URL=https://erp.example.com \
AMSAPI_ENCODING=gbk \
AMSAPI_AUTH_CLIENT_SECRET=$ERP_SECRET \
python main.py
```

## 四、档案字段全表

### 4.1 `[system]` — 仅用于展示

```ini
[system]
name = 商城/购物
description = body.success 判定 + Bearer 令牌
```

这两个字段只出现在日志和 Allure 报告的「环境」页，方便确认「这次跑的是哪套规则」。

### 4.2 `[env]` — 请求行为

```ini
[env]
base_url = https://api.example.com        ; 主域名（可被 AMSAPI_BASE_URL 覆盖）
timeout = 30                           ; 超时秒数
verify = false                         ; 是否校验 https 证书
encoding = gbk                         ; 强制响应编码（政务/财务老系统）
content_type = application/x-www-form-urlencoded   ; 默认请求体类型
response_format = auto                 ; auto | json | xml | text
```

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `base_url` | URL | 主域名。用例写相对路径时拼接 |
| `timeout` | 秒 | 留空则用 `conf.ini` |
| `verify` | `true`/`false` | 留空则用 `conf.ini` |
| `encoding` | `gbk`/`gb2312`/… | **留空=自动判断**（推荐）。只有自动判断出错时才强制 |
| `content_type` | MIME | 用例没写 `Content-Type` 时用这个 |
| `response_format` | `auto`/`json`/`xml`/`text` | 响应体怎么解析，见 [§八](#八请求体与编码) |

### 4.3 `[hosts]` — 域名别名（网关 + 多服务）

```ini
[hosts]
user   = https://user.example.com      ; 用户服务
order  = https://order.example.com      ; 订单服务
pay    = https://pay.example.com      ; 支付服务
```

用例里两种用法（等价）：

```yaml
# 方式一：内联前缀
url: order:/v1/orders

# 方式二：独立字段
url: /v1/orders
host: order
```

规则细节（都已用单元测试固定）：

- 别名**大小写不敏感**；未声明的别名会告警并回退主域名（不会静默发错地址）
- 前缀必须命中别名才会替换，所以 `/v1/a:b` 这种路径里的冒号**不会**被误当成域名
- 完整 URL（`http://...`）原样使用，不参与别名替换

> **前提**：`base_url` 或 `AMSAPI_BASE_URL` **为空**时才只看 `[hosts]`；
> 若显式指定了主域名，相对路径一律拼主域名。
> 因此多域名系统请把 `base_url` 留空（或只写网关地址）、用别名区分。
> 实际取值顺序：用例内联别名/`host` 字段 → 主域名。

### 4.4 `[headers]` / `[cookies]` — 系统级公共头与 Cookie

```ini
[headers]
X-Client = amsapi
App-Code = demo-app

[cookies]
X-Tenant = gs
lang = zh-CN
```

- **每次请求都会带上**，合并顺序：档案 < `BaseApi(headers=/cookies=)` < 单个请求的 `headers` / `cookies`
- 支持 `${var}` 占位符（值来自全局变量池），所以令牌型 Cookie 也能写在这里
- **请求头名保留大小写**（`X-Auth-Token` 不会被改成 `x-auth-token`）

> 什么时候用 `[headers]` 而不是 `[auth]`？
> 令牌类 → 用 `[auth]`（它还会自动处理取令牌、续期）；
> 非令牌的固定标识（客户端标识、租户、语言）→ 用 `[headers]` / `[cookies]`。

### 4.5 `[response]` — 成功怎么判（最关键的一段）

```ini
[response]
style = code                     ; 内置风格，见下表
success_path = body.code         ; 自定义业务码路径（覆盖风格的默认候选）
success_values = 0,200           ; 成功值集合；用例没写 expected_code 时用它
message_path = body.msg          ; 错误消息路径（不写则自动兜底找）
data_path = body.data            ; 业务数据体路径（分页/便捷属性用）
http_ok = 200,201,204            ; 视为成功的 HTTP 状态码
```

**六种内置风格**（`style`）：

| style | 业务码路径候选 | 成功值集合 | 典型系统 |
| --- | --- | --- | --- |
| `status` | `body.status` | （无，需用例给 expected_code） | 本工程原被测系统、多数政务 |
| `code` | `body.code` / `body.retCode` / `body.resultCode` | （无） | 财务、ERP、中台 |
| `success` | `body.success` / `body.ok` / `body.isSuccess` | `true,1,yes,ok` | 商城、现代前后端分离系统 |
| `errno` | `body.errno` / `body.errCode` / `body.errorCode` | `0,200` | 部分中台 |
| `retcode` | `body.retCode` / `body.retcode` / `body.returnCode` | `0000,0,200,success` | 银行、部分政务 |
| `raw` | 无（只看 HTTP 状态码） | （无） | 静态资源、无统一信封的系统 |

**判定语义**（记住这三条就够）：

```
用例给了 expected_code  →  用 expected_code 与「实际业务码」做宽松比较
用例没给 expected_code  →  用 success_values 集合判断实际业务码是否算成功
两者都没有              →  只看 HTTP 状态码（并打印一条"配置不完整"的告警，只打一次）
```

**宽松比较**：`200` 与 `"200"`、`true` 与 `"True"`、`0` 与 `0.0` 都算相等。
这样 Excel 里写 `200`、接口返回字符串 `"200"` 也能对上。

> `status` / `code` 这两种风格**没有**默认成功值集合，是刻意的：
> 这类系统的业务码有很多合法取值（分页结果码、查询成功码……），
> 猜一个默认值会导致「断言写漏了却全绿」。所以要求用例显式给 `expected_code`。

#### 不想做业务断言怎么办（令牌 / 下载 / 健康检查接口）

这类接口不遵循业务码信封，用 `check_business` 关掉业务断言，只保留字段断言：

```yaml
- title: 取令牌
  url: /oauth/token
  method: post
  check_business: false              # 不做业务码断言
  relation: token=body.access_token
  expects: "exists:body.access_token"
```

### 4.6 `[auth]` — 怎么鉴权

```ini
[auth]
type = header                        ; none | basic | bearer | header | apikey | cookie | oauth2
header = access-ticket               ; type=header 时的头名
token = ${ticket}                    ; 令牌值，支持 ${var}
```

| type | 附加字段 | 效果 | 典型系统 |
| --- | --- | --- | --- |
| `none` | — | 不附加任何东西（默认） | 内网只读接口 |
| `basic` | `username` `password` | `Authorization: Basic base64(u:p)` | 老政务、内部后台 |
| `bearer` | `token` `header`(默认 `Authorization`) `prefix`(默认 `Bearer `) | `Authorization: Bearer <token>` | 商城、中台、微服务网关 |
| `header` | `header` `token` `prefix` | 自定义头携带令牌 | 政务（`access-ticket`）、`X-Auth-Token` |
| `apikey` | `key_name` `token` `key_in`(`header`/`query`) | 请求头或 query 携带 API Key | 数据中台、开放平台 |
| `cookie` | `cookie_string` 或 `cookies` | 会话 Cookie | 传统 web、老 ERP |
| `oauth2` | `token_url` `client_id` `client_secret` `scope` `auth_mode` | 自动取令牌 + 缓存续期 | 中台、开放平台 |

**关键点：令牌值支持 `${var}`，且是「每次请求前」解析**（不是构造时解析一次）。
所以「先调登录接口拿 ticket，后续接口自动带上」这条链路，只要在档案里写 `token = ${ticket}` 即可，
用例里**完全不用写 `access-ticket` 头**。

`oauth2` 的细节：

- 首次请求前调用 `token_url`，按 `expires_in` 缓存，**到期前 60 秒自动续期**
- `auth_mode = post`（默认，client_id/secret 放表单）或 `basic`（走 HTTP Basic，部分平台要求）
- 取令牌失败会**直接抛错**，而不是让后续用例"莫名 401"

> 未识别的 `type` 会抛 `ValueError` 并列出全部可选值，不会静默不鉴权。

### 4.7 `[hooks]` — 签名 / 时间戳 / 加解密

```ini
[hooks]
before_request = common.hooks:make_timestamp_nonce_hook(), common.hooks:make_sign_hook({"salt": "abc", "upper": true})
after_response = common.hooks:make_decrypt_response_hook({"key": "0123456789abcdef", "fields": ["data"]})
```

三种声明写法：

| 写法 | 例子 | 说明 |
| --- | --- | --- |
| 直接引用函数 | `myhooks:add_trace` | 函数签名 `f(ctx) -> ctx` |
| 调用工厂（无参） | `common.hooks:make_timestamp_nonce_hook()` | **括号必须有** |
| 调用工厂（带 JSON 参数） | `common.hooks:make_sign_hook({"salt": "s"})` | 参数里的逗号不会被误切 |

多个钩子用**英文逗号**分隔，按声明顺序串行执行（前一个的产出传给后一个）。
漏写括号会直接报错并给出可照抄的写法：

```
ValueError: 钩子工厂需要调用后才生效（漏写括号了），请照下面任一形式书写：
    common.hooks:make_sign_hook()
    common.hooks:make_sign_hook({"salt": "xxx"})
```

**内置钩子工厂**：

| 工厂 | 作用 | 主要参数 |
| --- | --- | --- |
| `make_timestamp_nonce_hook` | 注入时间戳 + 随机串（防重放） | `fields` `ts_unit`(`s`/`ms`) `nonce_len` `ts_digits` |
| `make_sign_hook` | 参数排序拼串后摘要，写入报文或请求头 | `field` `salt` `alg` `upper` `exclude` `target`(`payload`/`header`) |
| `make_aes_hook` | AES 加密报文字段 | `key` `fields` `iv` `mode` `alg_field` |
| `make_decrypt_response_hook` | AES 解密响应字段 | `key` `fields` `iv` `mode` `drop_fields` |
| `make_token_response_hook` | 把响应里的令牌自动写进变量池 | `token_path` `var_name` |

**执行顺序（重要）**：

```
参数化 → 合并公共头 → 认证注入 → before_request 钩子 → 发送 → after_response 钩子 → 断言 / 关联提取
```

也就是说，**签名覆盖的是「认证之后」的完整报文**，而**断言与关联提取看到的是「解密之后」的报文**。
这正是实际系统需要的顺序（先带令牌再签名；先解密再校验字段）。

**签名工具**（可直接在自定义钩子里复用）：

```python
from common.hooks import digest, sign_sorted

digest("abc", alg="md5")                        # md5 / sha1 / sha256 / sha512
digest("abc", alg="hmac-sha256", key="secret")  # HMAC 系列
sign_sorted(params, salt="abc", alg="md5", upper=True, exclude=("sign",))
```

`sign_sorted` 覆盖了政务/财务/商城九成以上的签名套路：按 key 升序 → `k=v&k=v` → 追加盐值 → 摘要；
是否跳空值（`skip_empty`）、拼接符（`join`/`kv_sep`）、是否大写（`upper`）都可配。

**可选依赖**：AES / RSA 需要 `cryptography`，**没装也能跑**，相关功能会给出明确提示：

```bash
pip install cryptography     # 只有需要加解密时才装
```

### 4.8 可选依赖一览

| 能力 | 依赖 | 没装时的行为 |
| --- | --- | --- |
| JSON Schema 断言（`schema:`） | `jsonschema` | 该断言报错并提示安装；其它断言正常 |
| AES 加解密 / RSA 签名 | `cryptography` | 相关钩子/函数报错并提示安装；签名、时间戳、响应判定正常 |
| Allure 附件与步骤 | `allure-pytest` | 静默降级，测试照跑 |
| Allure HTML 渲染 | `allure` CLI + Java | 只产出 `allure-results/` |
| MySQL 数据源 | `PyMySQL` | 该数据源不可用，Excel/YAML 正常 |

框架**不会**因为缺少可选依赖而失败——这是设计约定，CI 里也因此不会因为环境差异误红。

## 五、五类系统接入示例

### 5.1 党政 / 政务系统

**典型特征**：`{"status": 200, "msg": "ok", "data": {...}}`；登录返回 `ticket`，后续接口放在
自定义头 `access-ticket`；偶尔 GBK 编码；有报文签名。

```ini
# config/systems/gov.ini
[system]
name = 党政/政务
description = body.status 判定 + access-ticket 票据

[env]
base_url =
timeout = 30
verify = false

[auth]
type = header
header = access-ticket
token = ${ticket}

[response]
style = status
message_path = body.msg
data_path = body.data
```

用例（Excel）：

| id | title | url | method | relation | expected_code | tags |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 登录系统 | `/v1/users/login` | get | `ticket=body.data.ticket` | 200 | smoke |
| 2 | 权限查询 | `/admin/resource/authority` | get | `None` | 200 | smoke |

**注意**：id=2 的 `headers` 列**留空**——票据由档案自动注入。
这正是"换系统不改用例"的体现。

### 5.2 财务 / ERP 系统

**典型特征**：`{"code": 200, "message": "..."}`；表单提交；会话 Cookie 或 `Token` 头；
参数签名（md5 + 盐）；GBK 编码；报文加密。

```ini
# config/systems/finance_erp.ini
[system]
name = 财务/ERP
description = body.code 判定 + 表单提交 + Cookie 会话 + 参数签名

[env]
base_url =
timeout = 30
content_type = application/x-www-form-urlencoded
; encoding = gbk                      ; 中文乱码时再打开

[auth]
type = cookie
cookie_string = JSESSIONID=

[response]
style = code
success_values = 0,200
message_path = body.message
data_path = body.data

[hooks]
before_request = common.hooks:make_timestamp_nonce_hook(), common.hooks:make_sign_hook({"salt": "", "upper": true, "exclude": "sign,timestamp"})
```

**要点**：

- `content_type` 声明一次，**所有用例都不用再写** `Content-Type`
- 财务系统常见的「排除时间戳参与签名」这类细节，用 `exclude` 配
- 中文乱码时才打开 `encoding = gbk`（自动判断通常已经正确）

### 5.3 商城 / 购物系统

**典型特征**：前后端分离；`{"success": true, "result": {...}}`；JWT Bearer；
多域名（主站 / 商品 / 订单 / 支付）；REST 风格（PUT / DELETE 带 JSON 体）。

```ini
# config/systems/mall.ini
[system]
name = 商城/购物
description = body.success 判定 + Bearer + 多域名

[env]
base_url =
timeout = 20

[hosts]
item  = https://item.example.com
order = https://order.example.com
pay   = https://pay.example.com

[auth]
type = bearer
token = ${token}

[response]
style = success
data_path = body.result
```

用例（YAML）：

```yaml
cases:
  - title: 登录领取令牌
    url: /api/v1/login
    method: post
    request_body: '{"username": "tester", "password": "***"}'
    relation: token=body.result.token
    expects: "exists:body.result.token"
    check_business: false

  - title: 商品列表（多域名：走 item 别名）
    url: item:/api/v1/items
    method: get
    expected_code: ~            # success 风格可不写，用档案的 success_values 判
    expects: "not_empty:body.result.items; gt:body.result.total=0"

  - title: 下单
    url: order:/api/v1/orders
    method: post
    request_body: '{"sku": "S-1", "num": 2}'
    relation: orderNo=body.result.orderNo

  - title: 批量删除（DELETE 带 JSON 体）
    url: order:/api/v1/orders
    method: delete
    headers: '{"Content-Type": "application/json"}'
    request_body: '{"ids": [1, 2]}'
    check_business: false
```

**要点**：

- `success` 风格下**用例可以不写 `expected_code`**，由档案的 `success_values` 判成功
- DELETE 想带 JSON 体，必须显式声明 `Content-Type: application/json`（否则走 query，见 [§八](#八请求体与编码)）

### 5.4 数据中台 / 信息系统

**典型特征**：OAuth2 或 API Key；网关 + 多服务；分页列表接口；`{"code": 0, "data": {"total": n, "items": [...]}}`。

```ini
# config/systems/dataplatform.ini
[system]
name = 数据中台
description = body.code 判定 + OAuth2 + 网关多服务

[env]
base_url = http://gateway.internal:8080
timeout = 60

[hosts]
meta  = http://meta.internal:8081
query = http://query.internal:8082

[auth]
type = oauth2
token_url = http://gateway.internal:8080/oauth/token
client_id = amsapi
client_secret = ***
scope = read
auth_mode = post

[response]
style = code
success_values = 0
data_path = body.data.items
```

列表分页抓取（手写用例里调用）：

```python
from api.base_api import BaseApi

api = BaseApi()
rows = api.paginate("/meta/v1/datasets", size=100, max_pages=50)
# 页码/页大小字段名不同时：
rows = api.paginate("/meta/v1/datasets", page_field="pageNum", size_field="limit", size=100)
# 自定义结束条件：
rows = api.paginate("/meta/v1/datasets", stop=lambda items, res: not items)
```

`data_path` 配成 `body.data.items` 后，`api.data` 与 `paginate()` 都直接拿到列表。

### 5.5 老系统 / XML 报文

**典型特征**：SOAP 或自定义 XML；业务码藏在 `response.status`；编码是 GBK。

```ini
[system]
name = 政务XML老系统

[env]
base_url = http://10.0.0.9:8081
response_format = xml
encoding = gbk

[response]
style = status
success_path = body.response.status     ; XML 转 dict 后根节点名是外层标签
data_path = body.response.data
```

XML → dict 的约定（`common/base.py`）：

```
<response><status>200</status><data><item id="1">A</item></data></response>
        ↓
{"response": {"status": 200, "data": {"item": {"@id": "1", "#text": "A"}}}}
```

- 属性 → `@属性名`；纯文本 → `#text`
- 数字/布尔自动转类型，所以 `equals:body.response.status=200` 能直接比对
- 命名空间会被剥离，不用关心前缀
- 反过来发 XML 报文：把 dict 放进 `request_body` 并声明 `Content-Type: application/xml`

## 六、断言与 `expects`

### 6.1 21 种内置算子

| 算子 | 说明 |
| --- | --- |
| `equals` / `not_equals` | 相等 / 不相等（宽松比较） |
| `contains` / `not_contains` | 包含子串（字符串）/ 元素（列表）/ 键（字典） |
| `startswith` / `endswith` / `regex` | 前缀 / 后缀 / 正则（包含匹配） |
| `type` | `str`/`int`/`float`/`bool`/`list`/`dict`/`none`/`number` |
| `exists` / `not_exists` | 字段存在且非 None / 不存在或为 None |
| `in` / `not_in` | 取值在 / 不在集合内（集合用逗号分隔） |
| `gt` / `ge` / `lt` / `le` | 数值比较 |
| `length` | 长度（字符串 / 列表 / 字典） |
| `empty` / `not_empty` | 为空 / 非空 |
| `elapsed` | 响应耗时不超过 N 毫秒 |
| `schema` | 响应体符合 JSON Schema（需 `jsonschema`） |

路径规则与 `relation` 一致：**根是完整响应**，响应体字段要带 `body.` 前缀。

### 6.2 两种写法（可混用）

```yaml
# 写法一：结构化（推荐，可读性好）
expects:
  - op: contains
    path: body.msg
    value: 操作成功
  - op: gt
    path: body.data.total
    value: 0

# 写法二：表格简写（Excel 里一列写完）
expects: "contains:body.msg=操作成功; gt:body.data.total=0; elapsed=3000"
```

简写规则：用 `;` 分隔多条；每条 `op:路径=期望值`；`=` 只按**第一个**切分，
所以期望值本身可以带等号（`equals:body.a=1=2` → expected 为 `1=2`）；
无期望值的算子可省略 `=值`（`exists:body.data`）。

### 6.3 在手写用例里用

```python
api = BaseApi()
api.request("get", "/v1/orders", data={"page": 1})

api.check_success(0)                       # 业务成功（规则来自档案）
api.check_status(200)                      # HTTP 状态码
api.assert_contains("body.msg", "成功")     # 字段级
api.assert_gt("body.data.total", 0)
api.assert_schema({"type": "object", "required": ["code"]})
api.check_expects("not_empty:body.data.items")   # 或一次给一批
```

## 七、用例生命周期

这三个字段（Excel 第 19~22 列 / YAML 字段）让「造数据 → 测 → 清理」写成一条用例，
不必再靠人工或外部脚本。

```yaml
- id: C100
  title: 新增商品并校验
  url: /api/v1/goods
  method: post
  request_body: '{"name": "测试商品", "price": 9.9}'

  # 前置：造数据（按顺序执行，支持 relation 提取给主请求用）
  setup:
    - url: /api/v1/categories
      method: post
      request_body: '{"name": "临时分类"}'
      relation: catId=body.data.id

  # 主请求（可用 ${catId}）
  depends: C001                 # 依赖的用例 id，逗号分隔

  # 后置：清理（断言失败也会执行）
  teardown:
    - url: /api/v1/categories/${catId}
      method: delete
```

| 字段 | 行为 | 注意 |
| --- | --- | --- |
| `setup` | 主请求之前按顺序执行 | 支持 `relation`，提取的变量主请求可用 |
| `teardown` | 主请求 + 断言之后执行 | **断言失败也执行**；清理自身报错只记日志，不掩盖原始失败 |
| `depends` | 依赖的用例必须已执行且通过 | 不满足 → 抛 `CaseSkipped` → 用例层转为 **skip**（不是 fail） |
| `check_business` | 是否做业务码断言，默认 `true` | 令牌/下载/健康检查类接口置 `false` |

> 为什么 `depends` 不满足是 skip 而不是 fail？
> 「前置没成功」不等于「本用例的实现有问题」。记成 fail 会污染失败率，
> 真正该看的是被依赖的那条用例。
>
> 被跳过的用例**不会被回写结果**（`res` 被清空），不会出现"上一条用例的响应记到了这一条"。

`setup` / `teardown` 的写法很灵活，以下都等价：

```yaml
setup: 'post /v1/goods'                                    # 单步简写
setup: '{"url": "/v1/goods", "method": "post"}'             # 单步 JSON
setup: [{"url": "/v1/goods", "method": "post"}]             # 列表
```

## 八、请求体与编码

### 8.1 挂载位置自动判定

数据挂到哪里由 **方法 × Content-Type** 决定（`RequestSend.body_location()`）：

| method | Content-Type | 挂到 |
| --- | --- | --- |
| `get` / `head` / `options` | 任意 | `params`（query） |
| `delete` | 未声明 | `params` |
| `delete` | `application/json` | `json` |
| `delete` | `x-www-form-urlencoded` | `data` |
| `delete` | `multipart/form-data` | `files` |
| `delete` | `application/xml` / `text/xml` / `text/plain` | `data`（原文） |
| `post` / `put` / `patch` | 未声明 / `application/json` | `json` |
| `post` | `x-www-form-urlencoded` | `data` |
| `post` | `multipart/form-data` | `files` |
| `post` | `application/xml` / `text/xml` / `text/plain` | `data`（原文） |

**这个判定只有一处实现**：请求层实际发送与 Allure 报告展示共用同一个函数，
所以报告里看到的「请求体 / 查询参数」永远与实际发出的一致。

### 8.2 响应编码

```ini
[env]
encoding = gbk            ; 只有自动判断出错时才需要
response_format = xml     ; auto | json | xml | text
```

| `response_format` | 行为 |
| --- | --- |
| `auto`（默认） | 先试 JSON，失败则原样给文本。**不做 XML 猜测** |
| `json` | 强制按 JSON 解析 |
| `xml` | 按 XML 解析成 dict（失败则回退文本） |
| `text` | 直接给原始文本 |

> `auto` 刻意**不**根据 `<` 开头去猜 XML：很多系统的错误页就是 HTML，
> 一旦猜错会把 `{html: ...}` 当成正常报文，断言失败原因会变得极难理解。
> XML 系统请显式声明 `response_format = xml`。

## 九、Excel 新增可选列速查

`test_case_list` 前 15 列保持不变；**第 16 列起为可选列，不填不影响旧用例**。

| 列号 | 列名 | 说明 |
| --- | --- | --- |
| O | `tags` | 原有：冒烟标签 |
| P | `host` | 域名别名（对应档案 `[hosts]`） |

## 十、常见系统差异速查

| 你遇到的现象 | 改档案的这一处 |
| --- | --- |
| 断言总失败，业务码在 `code` 而不是 `status` | `[response] style = code` |
| 成功就是 `true`，用例不想写 `expected_code` | `[response] style = success` |
| 业务码在很奇怪的地方（`body.biz.resultCode`） | `[response] success_path = body.biz.resultCode` |
| 令牌要放 `X-Auth-Token` 头 | `[auth] type = header` + `header = X-Auth-Token` |
| 令牌放 query 参数 | `[auth] type = apikey` + `key_in = query` |
| 要 OAuth2 自动取令牌 | `[auth] type = oauth2` + `token_url` … |
| 需要登录接口返回的 ticket 自动带上 | `[auth] token = ${ticket}`，用例用 `relation` 提取 |
| 请求要表单提交 | `[env] content_type = application/x-www-form-urlencoded` |
| 响应是 XML | `[env] response_format = xml` + `[response] success_path = body.<根标签>.<字段>` |
| 中文乱码 | `[env] encoding = gbk` |
| 多域名 / 多微服务 | `[hosts]` 段 + 用例 `host` 字段或 `别名:/path` |
| 要签名 | `[hooks] before_request = common.hooks:make_sign_hook({...})` |
| 要时间戳防重放 | `[hooks]` 加 `make_timestamp_nonce_hook()` |
| 报文加密 | `[hooks]` 加 `make_aes_hook({...})`（需 `cryptography`） |
| 固定客户端标识 / 租户 | `[headers]` / `[cookies]` |
| 令牌接口不该判业务码 | 用例置 `check_business: false` |
| 只想看 HTTP 状态码 | `[response] style = raw` |

## 十一、排查手册

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| `ConfigError: 未找到系统适配档案 'xx'` | 档案名写错或文件不存在 | 按报错里列出的可用档案改；或新建 `config/systems/xx.ini` |
| 报错 `钩子工厂需要调用后才生效` | 声明漏写括号 | 改成 `common.hooks:make_sign_hook()` 或带 JSON 参数 |
| 报错 `不支持的认证类型 'xxx'` | `[auth] type` 拼错 | 用报错里列出的 7 种之一 |
| 改了档案但不生效 | 档案是进程内缓存的 | 重启进程；或 `profile.clear_cache()` |
| 档案设了 `base_url` 但域名没生效 | `conf.ini` / `AMSAPI_BASE_URL` 优先级更高 | 清空 `conf.ini` 的 `base_url` |
| 域名别名不生效 | 主域名非空时相对路径一律拼主域名 | 把 `base_url` 留空，只在 `[hosts]` 里写 |
| `未声明域名别名 'xx'，回退主域名`（告警） | `hosts` 段里没写该别名 | 补上，或改用例的 `host` |
| 中文乱码 | 自动编码判断出错 | `[env] encoding = gbk` |
| 响应体变成一段 HTML 文本 | 服务端返回了错误页，或该声明 `response_format = xml` 没声明 | 先看日志里的响应体；XML 系统显式声明格式 |
| 断言失败但看不出原因 | 失败信息里已含服务端消息与响应摘要 | 看 Allure/日志里的「服务端消息」与「响应摘要」 |
| `schema:` 断言报错说没装依赖 | `jsonschema` 未安装 | `pip install jsonschema`，或用其它算子 |
| AES/国密相关报错说没装依赖 | `cryptography` 未安装 | `pip install cryptography` |
| 分页抓取卡住 | 服务端不翻页 | 已内置 `max_pages` 安全阀（默认 100），可调小 |
| 分页抓不到数据 | 列表不在默认路径 | 用例传 `data_path=` 或档案配 `[response] data_path` |

更多通用排错见 [常见问题 FAQ](05-常见问题FAQ.md)。

## 十二、在 CI 中使用

Jenkins 流水线已内置 `SYSTEM` 构建参数（见根目录 `Jenkinsfile`）。
命令行/其它 CI 直接注入环境变量：

```bash
# 用商城档案，跑冒烟，不回写数据源
AMSAPI_SYSTEM=mall AMSAPI_SMOKE=1 AMSAPI_WRITE_BACK=false \
python main.py --smoke --report allure
```

**用另一套档案 + 另一套数据（不改仓库文件）**：

```bash
AMSAPI_SYSTEM=mall \
AMSAPI_SYSTEMS_DIR=/ci/amsapi/systems \
AMSAPI_DATA_DIR=/ci/amsapi/data \
python main.py --smoke
```

> 这些**目录类**变量在进程启动时读取，属于"启动前就要定好"的参数，
> 与 `AMSAPI_BASE_URL` 这类运行期参数不同。

**报告里确认本次规则**：Allure 报告的「环境」页会打印
`系统档案 / 系统名称 / 主域名 / 域名别名 / 判定风格 / 业务码路径 / 成功值集合 / 认证方式 / 请求前钩子 / 响应后钩子`，
不含任何凭证。日志开头同样会打印一遍。

全部环境变量见 [CI/CD 集成 · 环境变量覆盖](06-CICD集成.md#三环境变量覆盖ci-的关键能力)。

## 十三、新增一个系统档案：Checklist

```
[ ] 1. cp config/systems/default.ini config/systems/<新系统>.ini
[ ] 2. 填 [system] name/description（便于报告里辨认）
[ ] 3. 填 [env] base_url / timeout / content_type / response_format / encoding
[ ] 4. 多域名系统填 [hosts]
[ ] 5. 填 [auth]（先在浏览器/Postman 里确认令牌放哪、头名是什么）
[ ] 6. 填 [response]（先手工看一眼成功与失败各长什么样，再定 style / success_path / success_values）
[ ] 7. 有签名/加密再填 [hooks]
[ ] 8. 先用 1~2 条最简单接口验证：python main.py --collect-only 确认用例被读到
[ ] 9. AMSAPI_SYSTEM=<新系统> python main.py --report none 跑一遍，看失败原因是否都落在「档案没配对」上
[ ] 10. 通了再跑全量；把关键差异记到档案注释里，方便下一个人
```

**调试技巧**：

```bash
# 只跑一条，看详细日志
AMSAPI_SYSTEM=mall python main.py -k id2001 -o log_cli=true -o log_cli_level=DEBUG
```

日志里会打印完整的 `【请求】` / `【关联】` / `【断言】` / `【适配】` 记录，
照着档案逐条核对即可。
