## 一、新增接口对象

### 1.1 何时需要新增

- 新增一个业务模块 → 新建一个 `api/xxx_api.py`
- 已有模块新增一个接口 → 在对应 `api/xxx_api.py` 里加一个方法

### 1.2 标准步骤

**第一步**：新建文件 `api/order_api.py`

```python
# -*- coding: utf-8 -*-
"""
订单接口对象
============
对应接口：
    GET    /v1/orders/detail     查询订单详情
    POST   /v1/orders/create     创建订单
    PUT    /v1/orders/update     全量更新订单
    PATCH  /v1/orders/status     局部更新（改状态）
    DELETE /v1/orders/delete     删除订单（无请求体，走 query）
    DELETE /v1/orders/batch      批量删除（带 JSON 请求体）
"""
from api.base_api import BaseApi


class OrderApi(BaseApi):
    """订单相关接口集合。"""

    # 路径写成类常量，避免路径散落在方法中
    DETAIL_PATH = "/v1/orders/detail"
    CREATE_PATH = "/v1/orders/create"
    UPDATE_PATH = "/v1/orders/update"
    STATUS_PATH = "/v1/orders/status"
    DELETE_PATH = "/v1/orders/delete"
    BATCH_PATH = "/v1/orders/batch"

    def get_detail(self, order_id):
        """
        查询订单详情。GET -> 数据自动进 query 参数。

        :param order_id: 订单号
        :return: 统一响应字典
        """
        return self.request("get", self.DETAIL_PATH, data={"orderId": order_id})

    def create(self, product_id, count, headers=None):
        """
        创建订单。POST 默认按 JSON 提交请求体。

        :param product_id: 商品 id
        :param count:      数量
        :param headers:    额外请求头（如需携带 access-ticket）
        """
        payload = {"productId": product_id, "count": count}
        return self.request("post", self.CREATE_PATH, data=payload, headers=headers)

    def update(self, order_id, **fields):
        """全量更新订单。PUT 同样默认走 JSON 体。"""
        payload = {"orderId": order_id}
        payload.update(fields)
        return self.request("put", self.UPDATE_PATH, data=payload)

    def change_status(self, order_id, status):
        """局部更新订单状态。PATCH 同样默认走 JSON 体。"""
        return self.request("patch", self.STATUS_PATH,
                            data={"orderId": order_id, "status": status})

    def remove(self, order_id):
        """删除单个订单。DELETE 未声明 Content-Type -> 数据进 query。"""
        return self.request("delete", self.DELETE_PATH, data={"orderId": order_id})

    def batch_remove(self, order_ids):
        """
        批量删除。DELETE 显式声明 JSON -> 数据进请求体。

        注意：这里必须带 `Content-Type: application/json` 请求头，
        否则会按 query 参数发送（见开发指南 1.5 挂载规则）。
        """
        return self.request("delete", self.BATCH_PATH,
                            data={"orderIds": list(order_ids)},
                            headers={"Content-Type": "application/json"})
```

**第二步**：在 `api/__init__.py` 中导出（可选，便于 `from api import OrderApi`）

**第三步**：在用例中调用

```python
api = OrderApi()
api.get_detail("ORDER001")
api.check_business_code(200)
assert api.body["data"]["orderId"] == "ORDER001"
```

### 1.3 编写要点

| 要点 | 说明 |
| --- | --- |
| 一个业务模块一个文件 | 命名 `xxx_api.py`，与 `test_xxx` 区分 |
| 路径写成类常量 | 路径变更时只改一处 |
| 方法名动词开头 | `get_detail` / `create` / `update_status` |
| 参数显式声明 | 不要用 `**kwargs` 一把梭，否则 IDE 无法提示 |
| 不写断言 | 断言属于用例层；接口层只负责"调通并返回" |
| 不写 `if/else` 业务分支 | 那是用例层的事 |
| 需要额外 header 时留 `headers` 参数 | 而不是在方法里硬编码 ticket |

### 1.4 需要携带 ticket 的接口

推荐在方法内自动注入，避免用例层重复写：

```python
from common.variable import GlobalVar

def get_authority(self, app_code):
    ticket = GlobalVar.get("ticket")
    return self.request("get", self.AUTHORITY_PATH,
                        data={"appCode": app_code},
                        headers={"access-ticket": ticket})
```

参考实现：`api/admin_api.py: get_authority_with_ticket()`

### 1.5 各 HTTP 方法的参数挂载规则

接口层只写 `self.request(method, path, data=...)`，**数据放在哪里由框架自动判定**，
不需要你手动区分 query 还是 body：

| method | 需要额外声明 Content-Type | 数据挂到哪里 |
| --- | --- | --- |
| `get` / `head` / `options` | 否 | query 参数 |
| `post` / `put` / `patch` | 否（默认 JSON） | 请求体（JSON） |
| `post` / `put` / `patch` | 是，`x-www-form-urlencoded` | 请求体（表单） |
| `post` / `put` / `patch` | 是，`multipart/form-data` | 文件上传 |
| `delete` | 否 | query 参数 |
| `delete` | 是，`application/json` | 请求体（JSON） |

三个容易踩的点：

1. **`delete` 想带请求体，必须显式写 `Content-Type: application/json`**。
   不写就按 query 发送，这也是为了兼容存量用例的默认行为。
2. **`get` 不支持请求体**（框架有意不提供）。GET 带 body 属反模式，
   多数网关会直接丢弃，写了容易"本地通、线上挂"。
3. **需要同时带 query 和 body** 的极少数场景，直接给 `send()` 传 `params=`：

   ```python
   api.request("post", "/v1/x", data={"b": 1}, params={"debug": 1})
   ```

> 完整判定表与设计理由见 [03-框架设计 · 4.9 请求体挂载规则](03-框架设计.md#49-请求体挂载规则http-方法--content-type)。

## 二、Excel 数据源

### 2.1 文件与 sheet

| 项 | 值 |
| --- | --- |
| 文件 | `data/api_tables.xlsx` |
| 用例 sheet | `test_case_list`（可由 `conf.ini` 的 `run.sheet_name` 修改） |

### 2.2 test_case_list 列含义

| 列 | 字段 | 必填 | 说明 |
| --- | --- | --- | --- |
| A | `id` | 是 | 用例编号，用于报告标题、`depends` 依赖与追溯 |
| B | `time` | — | **自动回写**：执行时间 |
| C | `title` | 是 | 用例标题，会出现在报告里 |
| D | `url` | 是 | 接口地址，可写完整地址、相对路径（需配 `base_url`）或 `别名:/路径`（多域名系统），支持 `${var}` |
| E | `method` | 是 | `get` / `post` / `put` / `delete` / `patch` / `head` / `options`，挂载规则见 [1.5](#15-各-http-方法的参数挂载规则) |
| F | `headers` | 否 | 请求头，**JSON 字符串**，支持 `${var}` |
| G | `cookies` | 否 | cookie，JSON 字符串 |
| H | `request_body` | 否 | 请求体，JSON 字符串（XML 系统可放 XML 原文），支持 `${var}` |
| I | `request_type` | 否 | 请求体类型（兼容列）；与 Q 列 `content_type` 等价，Q 列优先 |
| J | `relation` | 否 | 关联提取，如 `ticket=body.data.ticket`；多个用逗号分隔 |
| K | `expected_code` | 否 | 期望业务码。**是否必填取决于系统档案**：`status`/`code` 风格必填，`success`/`errno` 风格可留空 |
| L | `response` | — | **自动回写**：响应内容 |
| M | `ispass` | — | **自动回写**：是否通过 |
| N | `isdel` | 是 | `1` = 执行；其它值（或空）跳过 |
| O | `tags` | 否 | 用例标签，多个用逗号分隔，如 `smoke`、`smoke,core`。用于 CI/CD 冒烟筛选，见 [CI/CD 集成](06-CICD集成.md#二冒烟测试机制) |
| P | `host` | 否 | 域名别名，对应系统档案 `[hosts]` 段（网关 + 多服务的系统） |
| Q | `content_type` | 否 | 覆盖默认请求体类型（如 `application/x-www-form-urlencoded`） |
| R | `expects` | 否 | 字段级断言简写，如 `contains:body.msg=成功; gt:body.data.total=0` |
| S | `setup` | 否 | 前置步骤（造数据），JSON 数组或 `post /v1/x` 简写 |
| T | `teardown` | 否 | 后置清理步骤，JSON 数组；**断言失败也会执行** |
| U | `depends` | 否 | 依赖的用例 id，逗号分隔；前置未通过则本用例跳过（skip，不是 fail） |
| V | `check_business` | 否 | `1`/`0`，是否做业务码断言（默认 `1`）。令牌、文件下载、健康检查类接口填 `0` |

> **注意**：B、L、M 三列由框架回写，**不要手工填**。
>
> **P 列起为可选扩展列**，属于 2.4.0 新增的**系统适配能力**。
> 只写到 O 列的旧用例表**照常运行**（新增列读出来是 `None`，不影响既有用例）。
> 各列对应的系统差异见 [08-系统适配指南](08-系统适配指南.md#九excel-新增可选列速查)。

### 2.3 格式细节（容易踩坑）

| 场景 | 正确写法 | 错误写法 |
| --- | --- | --- |
| headers 为空 | 留空 或 `{}` | `None`（会被当字符串） |
| JSON 字符串 | `{"Content-Type": "application/json"}` | `{'Content-Type': 'application/json'}`（能用但不推荐） |
| 引用变量 | `{"access-ticket": "${ticket}"}` | `{"access-ticket": "$ticket"}`（少花括号） |
| 关联多个变量 | `a=body.data.a,b=body.data.b` | 用换行分隔 |
| 数字型 body | `{"page": 1}` | `{"page": "1"}`（类型不符可能被拒） |
| 多个标签 | `smoke,core` | `smoke、core`（顿号也能解析，但推荐逗号） |
| 多条字段断言 | `contains:body.msg=成功; gt:body.data.total=0` | 用换行分隔（简写只按 `;` 切） |
| 期望值本身带等号 | `equals:body.a=1=2`（只按第一个 `=` 切） | — |

> 框架用 `safe_loads()` 解析，**同时兼容 JSON 与 Python 字面量**写法
> （所以单引号也能解析），但仍**推荐用 JSON**，因为 YAML/MySQL 数据源
> 与工具链都按 JSON 标准工作。

### 2.4 执行顺序

**Excel 行序 = 执行顺序**。因此：

- 登录用例必须排在依赖 `ticket` 的用例**之前**
- 若需调整顺序，直接调整行位置即可

### 2.5 新增一条用例的操作步骤

1. 打开 `data/api_tables.xlsx` → `test_case_list` sheet
2. 在末尾新增一行
3. 填写 A、C、D、E、K、N 六列（其余按需）
4. 保存
5. 验证是否被读到：

```bash
python main.py --collect-only
```

6. 单条执行验证：

```bash
python main.py -k "idN"       # N 换成新用例 id
```

## 三、新增用例

### 3.1 三种方式怎么选

| 方式 | 适合 | 不适合 |
| --- | --- | --- |
| Excel | 业务同学维护、用例多且同构 | 需要复杂嵌套结构 |
| YAML | 开发维护、需要 diff、结构复杂 | 需要非技术人员维护 |
| MySQL | 多系统共用、需要集中管理 | 快速迭代阶段 |

### 3.2 方式一：Excel 用例

见 [第二节 · 新增一条用例的操作步骤](#25-新增一条用例的操作步骤)。

### 3.3 方式二：YAML 用例

**第一步**：在 `data/cases/` 下新建 `order.yaml`

```yaml
# 订单模块用例
cases:
  - title: 查询订单详情
    tags: [ smoke ]                 # 参与冒烟测试（CI/CD 构建后快速验证）
    url: /v1/orders/detail
    method: get
    headers:
      Content-Type: application/json
      access-ticket: ${ticket}      # 引用登录用例提取的变量
    cookies: { }
    request_body:
      orderId: ORDER001
    expected_code: 200
    isdel: 1
```

**第二步**：验证

```bash
python main.py --collect-only | grep order
python main.py -m yaml
```

**支持的两种文件结构**（二选一）：

```yaml
# 形式一：带 cases 键
cases:
  - title: xxx
    ...

# 形式二：文件本身就是列表
- title: xxx
  ...
```

**字段与 Excel 完全一致**（`title` / `url` / `method` / `headers` / `cookies` /
`request_body` / `relation` / `expected_code` / `isdel` / `tags`），只是用 YAML 语法表达。

**注意**：

| 项 | 说明 |
| --- | --- |
| 编码 | 必须 UTF-8，否则中文乱码 |
| 缩进 | YAML 对缩进敏感，统一用 2 空格，**不要用 Tab** |
| `isdel` | 不写时默认 `1`（参与执行） |
| `tags` | 参与冒烟筛选；可写 `[ smoke ]` 或 `smoke`（字符串） |
| 回写 | YAML 用例**不回写**结果 |
| `expected_code` 不写 | 只验证能正常请求，不做断言 |
| 文件加载顺序 | **按文件名升序**加载。依赖 `${ticket}` 的用例，其登录用例所在文件应命名靠前（如 `01-login.yaml`） |

### 3.4 方式三：MySQL 用例

见 [02-操作手册 · MySQL 数据源](02-操作手册.md#九mysql-数据源)。

### 3.5 方式四：手写 PO 风格用例（推荐给复杂流程）

数据驱动适合"同构的简单用例"。当流程复杂（多接口串联、分支断言）时，
直接手写 pytest 用例更清晰：

```python
# -*- coding: utf-8 -*-
"""订单流程用例"""
import allure
import pytest

from api.login_api import LoginApi
from api.order_api import OrderApi


@allure.epic("接口自动化")
@allure.feature("订单流程")
@pytest.mark.network                      # 依赖真实环境，可 -m "not network" 跳过
class TestOrderFlow:
    """下单完整流程。"""

    @allure.story("下单")
    @allure.title("登录 -> 创建订单 -> 查询订单")
    @allure.severity(allure.severity_level.CRITICAL)
    def test_create_order(self):
        # 1) 登录，ticket 自动进入变量池
        with allure.step("登录"):
            login = LoginApi()
            ticket = login.login_and_save_ticket("demo_user", "密码", "签名")
            login.check_business_code(200)
            assert ticket, "未取到 ticket"

        # 2) 创建订单
        with allure.step("创建订单"):
            api = OrderApi()
            api.create(product_id="P001", count=1)
            api.check_business_code(200)
            order_id = api.body["data"]["orderId"]

        # 3) 查询验证
        with allure.step("查询订单校验"):
            api.get_detail(order_id)
            # 路径根为完整响应，所以响应体字段要写 body.xxx
            api.check_json("body.data.orderId", order_id)
            api.check_json("body.data.count", 1)
```

**手写用例的四条规范**：

1. 每个关键动作包一个 `with allure.step(...)`，报告中形成步骤树
2. 断言用 `check_*` 方法 或 原生 `assert`，后者需带清晰的失败信息
3. 依赖真实环境的用例打 `@pytest.mark.network`
4. 需要参与 CI 冒烟测试的用例，打 `@pytest.mark.smoke`
   （数据驱动用例通过 `tags` 字段标记，手写用例用 marker；详见 [CI/CD 集成](06-CICD集成.md#21-如何标记冒烟用例)）

**手写用例与数据驱动的选择**：

| 场景 | 推荐 |
| --- | --- |
| 同构的简单接口校验 | 数据驱动（Excel / YAML） |
| 多接口串联、分支判断、复杂断言 | 手写用例 |
| 需要作为 CI 冒烟用例 | 两者都可以：数据驱动打 `tags`，手写用例打 `@pytest.mark.smoke` |

参考实现：`testcase/test_login.py`

## 四、新增断言

### 4.1 内置断言够用吗

2.4.0 起内置了 **21 种字段级断言算子**，绝大多数场景直接配 `expects` 即可，
**不需要写代码**：

| 需求 | 用什么 |
| --- | --- |
| 验 HTTP 状态码 | `check_status(200)` / `expects: "equals:code=200"` |
| 验业务成功（按系统规则） | `check_success(0)` — 规则来自系统档案，换系统不用改 |
| 验业务码（固定 `body.status`） | `check_business_code(200)`（兼容存量） |
| 验某个字段值 | `assert_equals("body.data.id", 123)` |
| 验包含 / 正则 / 前缀后缀 | `assert_contains` / `assert_regex` / `assert_startswith` / `assert_endswith` |
| 验列表非空 / 长度 | `assert_not_empty("body.rows")` / `assert_length("body.rows", 10)` |
| 验数值范围 | `assert_gt` / `assert_ge` / `assert_lt` / `assert_le` |
| 验类型 | `assert_type("body.data.total", "number")` |
| 验响应耗时 | `assert_elapsed(3000)` |
| 验响应结构（JSON Schema） | `assert_schema({...})`（需可选依赖 `jsonschema`） |

完整算子清单见 [系统适配指南 · 断言与 expects](08-系统适配指南.md#六断言与-expects)。

### 4.2 在用例中组合断言

**方式一：数据里配 `expects`（推荐，不用写代码）**

```yaml
- title: 订单列表
  url: /v1/orders
  method: get
  expected_code: 0
  expects:
    - op: not_empty
      path: body.data.items
    - op: gt
      path: body.data.total
      value: 0
    - op: elapsed
      value: 3000
```

Excel 里则写成一列：`not_empty:body.data.items; gt:body.data.total=0; elapsed=3000`

**方式二：手写用例里直接调**

```python
api.get_detail("ORDER001")

api.check_status(200)                             # HTTP 层
api.check_success(0)                               # 业务层（按系统档案判定）
api.assert_equals("body.data.orderId", "ORDER001")  # 字段层
api.assert_not_empty("body.data.items")
api.assert_gt("body.data.total", 0)
api.check_expects("elapsed=3000")                  # 也能一次给一批
```

> 字段路径的**根是完整响应**，所以响应体字段要带 `body.` 前缀；
> `code` 指 HTTP 状态码（响应字典的顶层键）。

### 4.3 新增一个断言算子

只有当内置 21 个算子都不够时，才需要扩展。在 `common/asserts.py` 中新增：

```python
@op("list_not_empty", needs_value=False, aliases=("listnotempty",))
def list_not_empty(response, path, msg=""):
    """
    断言指定路径是「非空列表」。

    :param path: 以完整响应为根的路径，如 "body.data.items"
    """
    actual = value_of(response, path)
    if not isinstance(actual, list) or not actual:
        _fail("{}应为非空列表，实际为 {!r}".format(msg, actual), response, path)
    return True
```

**规范**：

- 用 `@op("名字", needs_value=..., aliases=(...))` 注册：
  `needs_value=False` 表示该算子不需要期望值（如 `exists` / `empty`）；
  `aliases` 可挂简写别名
- **必须同步在 `OP_DOC` 里补上用途说明**——`expects` 写错算子名时，报错信息会列出这份清单
- 断言失败一律走 `_fail(消息, response, path)`，它会统一附上「字段路径 + 响应摘要」
- 成功返回 `True`
- 辅助函数：`value_of(response, path)` 取值、`summary(response)` 响应摘要、
  `base_equals(a, b)` 宽松比较、`_to_number(...)` 安全转数字
- 补充中文 docstring（本项目要求全中文注释）

> 新增算子后，`tests/test_common_asserts.py` 会自动校验
> 「`OP_DOC` 里的每个算子都已注册」，漏注册会在单测里直接暴露。

## 五、新增数据源

框架最重要的扩展点。以新增「CSV 数据源」为例。

### 5.1 三步走

**第一步**：写 loader，产出统一的用例 dict 列表

```python
# utils/csvutil.py
# -*- coding: utf-8 -*-
"""CSV 用例读写工具层"""
import csv
import os

from config import settings
from utils.logutil import logger


def read_cases(path=None):
    """
    读取 CSV 用例，返回统一契约的 dict 列表。

    必备字段：url / method；可选：headers / cookies / request_body /
              relation / expected_code / isdel
    """
    path = path or os.path.join(settings.DATA_DIR, "cases.csv")
    cases = []
    with open(path, "r", encoding="utf-8-sig", newline="") as fp:
        for index, row in enumerate(csv.DictReader(fp), start=2):
            row["isdel"] = row.get("isdel") or 1
            row["__row__"] = index
            cases.append(row)
    logger.info("从 {} 读取到 {} 条 CSV 用例".format(path, len(cases)))
    return cases
```

**第二步**：写 driver，产出 pytest 用例

```python
# testcase/test_csv_driver.py
# -*- coding: utf-8 -*-
"""CSV 数据驱动用例"""
import allure
import pytest

from utils.csvutil import read_cases

CASES = read_cases()

if not CASES:
    pytest.skip("CSV 用例为空", allow_module_level=True)


@allure.epic("接口自动化")
@allure.feature("CSV 数据驱动")
@pytest.mark.csv
class TestCsvDriver:

    @pytest.mark.parametrize("case", CASES, ids=lambda c: c.get("title", "case"))
    def test_api(self, case, api_client):
        allure.dynamic.title(case.get("title"))
        res = api_client.run_case(case)

        expected = case.get("expected_code")
        if expected is None:
            return
        body = res.get("body")
        actual = body.get("status") if isinstance(body, dict) else None
        assert actual is not None and int(actual) == int(expected), \
            "业务状态码不符：期望 {}，实际 {}".format(expected, actual)
```

在 `testcase/conftest.py` 的 `pytest_configure` 中加一行：

### 5.2 数据契约（必须遵守）

loader 产出的每个 dict 必须含：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `url` | 是 | 接口地址 |
| `method` | 是 | 请求方法 |
| `headers` | 否 | JSON 字符串或 dict |
| `cookies` | 否 | JSON 字符串或 dict |
| `request_body` | 否 | JSON 字符串或 dict |
| `relation` | 否 | 关联表达式 |
| `expected_code` | 否 | 期望业务码 |
| `isdel` | 否 | `1` 才执行 |
| `tags` | 否 | 标签（字符串或列表），用于冒烟筛选 |

> **只要遵守这个契约，接口层与断言逻辑完全不用改**——这就是分层带来的收益。
> 详见 [03-框架设计 · 数据源抽象](03-框架设计.md#47-数据源抽象)。

### 6.1 放置原则

### 6.2 编写规范

```python
# -*- coding: utf-8 -*-
"""
文件加密工具
============
提供 MD5 / SHA256 计算，供接口签名使用。

用法：
    from utils.cryptoutil import md5
    sign = md5("abc")
"""
import hashlib

from utils.logutil import logger


def md5(text):
    """
    计算字符串的 MD5 值。

    :param text: 待计算的字符串
    :return: 32 位小写十六进制字符串
    """
    value = hashlib.md5(str(text).encode("utf-8")).hexdigest()
    logger.debug("md5({}) = {}".format(text, value))
    return value


if __name__ == "__main__":
    # 自测：python -m utils.cryptoutil
    print(md5("abc"))
```

**要点**：

1. 模块级 docstring 说明**用途 + 用法**
2. 每个函数带参数与返回值说明
3. 末尾加 `if __name__ == "__main__":` 自测块，便于单独验证
4. 不 import 上层（`api` / `testcase`）
5. 可选依赖用 `try/except ImportError` 降级（参考 `allureutil.py` / `mysqlutil.py`）

## 七、编码规范

### 7.1 命名

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 模块（工具） | 小写下划线 | `requestsutil.py` |
| 接口对象文件 | 业务名 + `_api` | `login_api.py` |
| 用例文件 | `test_` + 来源/业务 | `test_excel_driver.py`、`test_login.py` |
| 类 | 大驼峰 | `LoginApi`、`ExcelUtil` |
| 函数/方法 | 小写下划线，动词开头 | `get_detail`、`read_cases` |
| 类常量 | 全大写下划线 | `LOGIN_PATH` |
| 关联变量名 | 小驼峰，带业务前缀 | `ticket`、`orderId` |

### 7.2 注释

本项目要求**全中文注释**，规范如下：

| 位置 | 要求 |
| --- | --- |
| 模块级 | docstring 说明「用途 + 分层职责 + 用法示例」 |
| 类 | 一行说明这个类是干什么的 |
| 公共方法 | 说明参数、返回值、异常；复杂逻辑补充「为什么」 |
| 关键行 | 行内注释解释**非显而易见**的意图，而不是复述代码 |
| 分隔 | 用 `# ---- 分区名 ----` 或 `# ===== 分区名 =====` 划分逻辑区块 |

**反例**（无价值）：

```python
i += 1        # i 加一        ← 复述代码
```

**正例**（解释意图）：

```python
# 用真实物理行号回写，避免旧实现「行号 = id + 1」的脆弱假设
self.sheet.cell(row=row, column=CASE_COLUMNS["time"]).value = now
```

### 7.3 异常处理

| 原则 | 说明 |
| --- | --- |
| 不吞异常 | 除非是可选功能降级，否则记录日志后重新抛出 |
| 降级要显式 | 如 `allureutil`、`mysqlutil` 的 `ImportError` 处理 |
| 断言失败给足信息 | 必须包含期望值与实际值 |
| 网络异常向上抛 | `requestsutil` 捕获后 `raise`，由用例层记为失败 |

```python
# 降级示例（可选依赖）
try:
    import pymysql
except ImportError:
    pymysql = None        # 不阻塞其它模块导入
```

### 7.4 配置（禁止硬编码）

**一句话原则**：凡是「换个环境可能就不一样」的东西，一律不许写在代码里。

| 规则 | 说明 |
| --- | --- |
| 路径统一从 `config/settings.py` 取 | 禁止在业务代码里拼 `os.path` |
| 可调参数放 `conf.ini` | 超时、域名、数据源、日志级别、报告标题、OAuth2 参数、CI 判定变量、脱敏、代理 |
| 配置分组 | `[env]` `[run]` `[db]` `[report]` `[log]` `[auth]` `[ci]` `[mask]` `[network]`；代码侧对应 `RunConfig` / `DB_CONFIG` / `ReportConfig` / `LogConfig` / `AuthConfig` / `CIConfig` / `MaskConfig` / `NetworkConfig` |
| 优先级 | `AMSAPI_*` 环境变量 > `conf.ini` > `settings.py` 默认值；**空字符串视为未设置** |
| 新增配置项 | 四处都要动：`settings.py` 加类属性 + `conf.ini` 加项并写注释 + `_load_env()` 加环境变量映射 + 文档同步（`README.md` 配置速查 / `docs/02-操作手册.md`） |
| 系统差异 | 不写进代码，写进 `config/systems/*.ini` 档案（见 [08-系统适配指南](08-系统适配指南.md)） |
| 不用代码逻辑写死域名/账号 | 用 `base_url`、系统档案或 `AMSAPI_*` |
| 不提交密码 / 真实地址 / 真实数据 | 仓库内所有凭据字段留空；示例用 `demo_user` / `https://api.example.com` / `192.0.2.10` / 相对路径 |
| 敏感字段不外泄 | 新增会输出请求/响应的代码路径时，确认它经过 `utils/logutil`（日志）或 `utils/allureutil`（报告附件）；**不要自己 `print` 原始报文** |
| 含 `%` 或 `${}` 的 INI | 读的时候必须 `ConfigParser(interpolation=None)`，否则抛 `InterpolationSyntaxError` |

```python
# ❌ 硬编码：换个环境就要改代码
TIMEOUT = 30
LOG_FILE = "amsapi.log"
if os.environ.get("JENKINS_URL"):   # 写死的判定变量清单

# ✅ 从配置中心取：换环境只改配置/环境变量
from config import settings
timeout = settings.RunConfig.TIMEOUT
log_file = settings.LogConfig.file_name()
if any(os.environ.get(k) for k in settings.CIConfig.DETECT_ENV_VARS):
    ...
```

> 自查手段：`python -m pytest tests/test_repo_sanitized.py -q`（开源守卫）+
> 全局搜 `http://` / `https://` / 裸数字超时 / 裸文件名。

## 八、提交与协作规范

### 8.1 提交前自检

```bash
# 1. 语法检查
python -m compileall -q api common config utils testcase tools main.py

# 2. 风格检查（0 问题才算过）
python -m flake8 .

# 3. 环境预检（依赖 / 配置 / 数据 / 目录 / 目标连通性）
python tools/preflight.py

# 4. 框架单元测试（改了框架代码必跑，离线约 10 秒）
python -m pytest tests -q

# 5. 确认用例能被收集
python main.py --collect-only

# 6. 本地跑一遍
python main.py --report none
```

> **改了 `api/` `common/` `utils/` `config/` `main.py` 却只跑第 1、5、6 步是不够的**——
> 那几步不会验证你的改动是否正确，只会验证「没崩」。
> 请为改动的行为补 `tests/` 用例，详见 [07-单元测试](07-单元测试.md)。
>
> 若改动的代码路径会打印请求/响应，**顺手确认它没有被 `mask` 漏过**
> （日志走 `utils/logutil`、报告附件走 `utils/allureutil` 即自动脱敏）。
