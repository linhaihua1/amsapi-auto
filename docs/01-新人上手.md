# 新人上手指南（30 分钟跑通）

> 本文面向**第一次接触本框架**的开发/测试同学。
> 目标：读完本文，你能在本机跑通测试、看懂报告、并知道下一步该做什么。
>
> **只想读一份文档就把项目接手？** 看
> [00-新手完整指引](00-新手完整指引.md) —— 它把「看哪 / 写用例 / 跑用例 / 接 Jenkins / 接 CI/CD」
> 串成了一条线。本文则更聚焦「环境准备与第一次跑通」。

---

## 一、这个框架是什么

一句话：**用 Excel / YAML / 数据库存用例，用 pytest 跑接口，产出 Allure 报告。**

它的核心价值不是"能发请求"，而是：

| 能力 | 解决什么问题 |
| --- | --- |
| 数据驱动 | 加用例不改代码，业务同学也能维护（改表格即可） |
| PO 分层 | 接口地址/参数只写一遍，接口变更时改一处 |
| 参数关联 | 登录拿到的 ticket 自动传给后续接口，不用手工复制 |
| 多数据源 | Excel / YAML / MySQL 随意切换，执行逻辑不变 |
| Allure 报告 | 每条用例带步骤树 + 请求响应附件，失败一眼定位 |

## 二、前置知识

不需要精通，但建议了解以下概念，遇到不懂能查：

| 概念 | 为什么需要 | 建议投入 |
| --- | --- | --- |
| Python 基础语法 | 读/改用例、写接口对象 | 必须 |
| pytest 基础 | 用例收集、参数化、fixture、marker | 半天 |
| requests 基础 | 理解 HTTP 方法、headers、body | 1 小时 |
| REST / JSON | 看懂响应结构、写关联表达式 | 1 小时 |
| Allure 报告 | 看懂报告、定位失败 | 20 分钟 |

> 不熟悉 pytest 的话，重点看三件事：`@pytest.mark.parametrize`（参数化）、
> `conftest.py`（全局配置）、`-m` / `-k`（筛选用例）。其余用到再查。

## 三、环境准备

### 3.1 必需

| 项 | 版本要求 | 校验命令 |
| --- | --- | --- |
| Python | 3.7+（建议 3.10+） | `python --version` |
| pip | 随 Python | `pip --version` |

### 3.2 可选（只为生成 Allure HTML 报告）

| 项 | 说明 | 校验命令 |
| --- | --- | --- |
| Java | Allure CLI 的运行依赖 | `java -version` |
| Allure CLI | 把原始结果渲染成 HTML | `allure --version` |

> 没装 Allure 也能跑测试，只是不生成 HTML 报告。装法见
> [02-操作手册 · 报告](02-操作手册.md#六测试报告)。
> 部分环境（如公司内网镜像）已内置，先执行 `allure --version` 确认。

### 3.3 安装依赖

```bash
# 进入项目根目录
cd amsapi-auto

# 安装依赖
pip install -r requirements.txt
```

如果公司有内网镜像，加 `-i` 指定源：

```bash
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

> **推荐使用虚拟环境**，避免污染本机 Python：
> ```bash
> python -m venv venv
> # Windows
> venv\Scripts\activate
> # macOS / Linux
> source venv/bin/activate
> pip install -r requirements.txt
> ```

### 3.4 验证环境

```bash
# 1) 语法自检（不执行任何请求）
python -m compileall -q api common config utils testcase tools main.py

# 2) 环境预检：依赖 / 配置 / 用例数据 / 可写目录 / 目标连通性，一次看清
python tools/preflight.py

# 3) 风格检查（改过代码就跑）
python -m flake8 .
```

输出为空且无报错 = 环境正常。
`preflight.py` 会分「错误 / 警告 / 提示」三档输出：**有「错误」先修，「警告」多为可选依赖未装**。

> 若本机配了系统代理（`HTTP_PROXY`），预检里对 `127.0.0.1` 的连通性检测同样会**自动绕过代理**，
> 不需要手动设 `NO_PROXY`。

## 四、5 分钟跑通

### 步骤 1：确认配置

打开 `config/conf.ini`，确认关键四项：

```ini
[env]
base_url =                    ; 留空表示用例自己写全 url
system = default              ; 系统适配档案；接别的系统改这里（见 08-系统适配指南）

[run]
data_source = excel           ; 先用 Excel 数据源上手

[report]
report_type = allure          ; 报告类型
```

> `system = default` 是内置默认档案，**行为与改造前完全一致**。
> 只有当你要接**别的 web 系统**（改判定规则、认证方式、签名…）时才需要动它，
> 详见 [08-系统适配指南](08-系统适配指南.md)。

### 步骤 2：起本地 mock 服务（手里没有可访问的被测系统时必做）

仓库内置了一个零依赖的 mock 服务，把示例接口在**你本机**复刻出来，
不连内网也不连外网 —— 这样任何人都能先把框架跑通再谈接真实系统。

```bash
# 终端 A：保持开着（默认 127.0.0.1:18080）
python tools/mock_server.py
```

> 已有可访问的被测系统 → 跳过这一步，直接在步骤 3 用你自己的地址。

### 步骤 3：执行

```bash
# 用 mock 跑（示例用例 + 示例接口，全链路自证）
AMSAPI_BASE_URL=http://127.0.0.1:18080 python main.py -m yaml

# 已有自己的被测系统（改地址即可，其余不用动）
# AMSAPI_BASE_URL=https://your-host python main.py
```

### 步骤 4：看结果

终端会依次打印：

```
======================================================================
接口自动化测试 启动
项目根目录 : /path/to/amsapi-auto
运行环境   : test
系统档案   : default
数据源     : yaml
结果回写   : True
敏感脱敏   : 开启（partial）
CI 环境    : 否
报告类型   : allure
Allure 数据: /path/to/amsapi-auto/report/allure-results
pytest 参数: -m yaml
======================================================================
...
testcase/test_yaml_driver.py::TestYamlDriver::test_api[id1[登录并提取票据]] PASSED
testcase/test_yaml_driver.py::TestYamlDriver::test_api[id2[按 id 查询字典]] PASSED
...
```

末尾出现 `5 passed, 1 skipped` 之类的汇总，即为跑通。
（`skipped` 来自示例里那条「依赖未满足会被跳过」的演示用例，属预期。）

### 步骤 5：看报告

```bash
python tools/generate_report.py --open
```

浏览器会自动打开 `report/allure-report/index.html`。

### 步骤 6：看日志

```bash
# 日志按天存放在 log/ 下
ls log/
```

日志比报告更详细，包含每条请求的 headers / params / body 与响应体。

> 日志里的口令、令牌会显示为 `dem****rd` 这类形态 —— 那是**脱敏默认开启**，
> 属于保护机制而不是故障。想临时看原文：`AMSAPI_MASK_SENSITIVE=false python main.py ...`（仅本地调试）。
> 日志文件按大小轮转（默认 20MB × 5 份），并按保留天数自动清理**框架自己生成**的历史日志。

## 五、新人第一天 Checklist

按顺序做完，你就完全接手这个项目了。

- [ ] 读完本文，跑通 `python main.py -m yaml`（配合 `tools/mock_server.py`）
- [ ] 跑一次框架单元测试 `python -m pytest tests`，确认本地环境完整（离线，10 秒）
- [ ] 跑一次 `python tools/preflight.py`，知道环境问题怎么被提前发现
- [ ] 打开 Allure 报告，随便点开一条**失败/跳过**的用例，看懂步骤树
- [ ] 打开 `log/` 下当天的日志，找到"【请求】"与"【关联】"两行，理解请求链路
- [ ] 打开 `data/api_tables.xlsx` 的 `test_case_list` 表，对照 [04-开发指南 · 列含义](04-开发指南.md#二excel-数据源) 看懂每一列
- [ ] 打开 `data/cases/login.yaml`，理解 `${ticket}` 是怎么传下去的
- [ ] 找到 `api/login_api.py`，看接口是怎么被封装的
- [ ] 改一条用例的 `expected_code` 为错误值，跑一次，观察失败表现（**改完记得改回来**）
- [ ] 扫一眼 `examples/` 三套对照示例（商城 / 中台 / 老系统），知道换系统该看哪
- [ ] 读完 [03-框架设计](03-框架设计.md)，画出执行流程图（能画出来说明懂了）
- [ ] 按 [04-开发指南](04-开发指南.md) 新增一条自己的用例，跑通
- [ ] 读一遍 [07-单元测试](07-单元测试.md)，知道改框架代码后要跑什么

对应的**代码阅读顺序**（配合文档看）：

```
1. main.py                     入口，先看它怎么起 pytest
2. config/conf.ini             配置长什么样
3. config/settings.py          配置怎么被读取
4. testcase/test_excel_driver.py   一条用例怎么被执行的
5. api/base_api.py             ★ 核心，请求/参数化/认证/关联/断言都在这
6. common/base.py              ${var} 替换与路径取值
7. common/profile.py           ★ 系统适配档案：不同系统的差异都收在这
8. utils/requestsutil.py       HTTP 请求怎么发的
9. utils/excelutil.py          Excel 怎么读、结果怎么回写
```

> **重点**：`api/base_api.py` 是理解整个框架的钥匙。
> 看懂它的几个方法（`request` / `extract` / `check_*` / `run_case` / `paginate`），框架就没有秘密了。
> 只需要测一个固定系统时，`common/profile.py`、`auth.py`、`hooks.py` 可以先跳过。

> **阅读顺序里刻意没有 `tests/`**：那是「框架自测」的代码，一进去先撞上的是替身对象、
> monkeypatch、tmp_path 这些**测试技巧**，而不是框架本身的设计思路 —— 容易把
> 「怎么被验证的」误当成「它是怎么设计的」。按上面 8 步读完再回头看
> [07-单元测试](07-单元测试.md)，会顺很多。
>
> 同理，**接新系统时才需要读** `common/auth.py`（认证策略）、`common/response.py`（成功判定）、
> `common/hooks.py`（签名加密）、`common/asserts.py`（断言算子）—— 这四个模块由
> [08-系统适配指南](08-系统适配指南.md) 按「要解决什么问题」组织，比按代码顺序读更好懂。

## 七、目录速查

```
amsapi-auto/
├── config/        配置层：改这里切换环境与数据源
│   ├── conf.ini       ★ 日常最常改的文件
│   ├── settings.py    配置读取逻辑
│   └── systems/       ★ 系统适配档案：接别的 web 系统改这里
├── common/        公共层：参数化、变量池、档案、认证、响应判定、钩子、断言
│                  （另有 mask.py 敏感信息脱敏、metadata.py 执行元数据）
├── utils/         工具层：HTTP / Excel / YAML / MySQL / 日志（含脱敏与轮转）/ Allure 封装
├── api/           ★ 接口层：接口对象写在这里
├── testcase/      ★ 用例层：日常写用例就在这里
├── tests/         框架单元测试（离线自测，改框架代码后跑 `pytest tests`）
│                  ⚠️ 不是业务用例目录，写用例请去 testcase/ ← 新手最容易混的地方
├── data/          ★ 数据层：用例数据（全部为通用示例数据）
│   ├── api_tables.xlsx   Excel 用例
│   └── cases/*.yaml      YAML 用例
├── examples/      ★ 三套对照示例：商城 / 数据中台 / 老系统（XML+GBK+签名）
├── tools/         辅助脚本：报告生成、本地 mock 服务、环境预检（tools/preflight.py）
├── docs/          本文档目录
├── main.py        统一入口
├── Jenkinsfile    CI/CD 流水线定义（接 Jenkins 时用）
├── .flake8        风格检查配置（`python -m flake8 .`）
├── requirements.txt / requirements-dev.txt   运行依赖 / 开发依赖
├── report/        报告输出（自动生成，勿手工改）
├── log/           运行日志（自动生成）
└── legacy/        旧版本文件归档，不参与运行
```

带 ★ 的是日常最常接触的四处：改配置（`config/conf.ini`）、看接口（`api/`）、
写用例（`testcase/`）、添数据（`data/`）；接一个新系统时再加一处 `config/systems/`。

> **手里没有被测系统？** 先跑 `python tools/mock_server.py`，
> 再用 `AMSAPI_BASE_URL=http://127.0.0.1:18080` 跑一遍 —— 全链路可自证，
> 详见 [02-操作手册 · 2.6 不连内网也能跑通](02-操作手册.md#26-不连内网也能跑通离线体验)。

> **别把 `tests/` 和 `testcase/` 搞混**：名字只差一个字母，职责完全相反 ——
> `testcase/` 测**你的业务系统**（要连内网），`tests/` 测**框架自己**（完全离线）。
> 写用例去 `testcase/`，`tests/` 只在改了框架代码后才需要碰。
